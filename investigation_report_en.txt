0. PREFACE AND DISCLAIMER
================================================================================

This document is a defensive security audit — a defensive cryptographic
investigation of a random-number-generator (RNG) vulnerability in the Coldcard
Mk3 hardware wallet manufactured by Coinkite Inc.

All seed-recovery work was performed for research purposes, to establish the
full scope of an already-completed theft. The recovered mnemonics and private
keys are NOT published and NOT included in this document. Funds on every
identified address have already been stolen by the attacker (balance = 0 across
100% of addresses); recovering the seeds created no new risk for victims, but it
exposed the full picture of the incident that is unavailable to public analysts.

This report is intended for hand-off to law enforcement (LE), blockchain-forensic
firms (Chainalysis, TRM Labs), and for coordination with exchanges (CEXes) on
monitoring the consolidation addresses.

All attacker-infrastructure addresses (bots, consolidation hubs, mixers) are
given in full, as they are already public and their disclosure serves the
investigation. Victim addresses are truncated in the body of the report; the
full list of 35,189 addresses is delivered as a separate appendix.

0.1 SCOPE & LIMITATIONS
================================================================================

This report establishes a LOWER BOUND on the damage; it does not claim 100%
coverage of those affected. The bounds are stated up front so the reader
(including LE) interprets the figures correctly.

WHAT IS COVERED (high confidence):
  - 2,052 Mk3 seed phrases recovered (~99%+ of the recoverable Mk3 population,
    ceiling ~2,070 by independent saturation signals).
  - Overlap with the official victim list: 4,407 / 6,541 (67.4%); the full set

  - Net Stolen of 5,079.90 BTC is computed from the full graph of 46,131
    transactions (100% balance coverage), robust to the "these are internal
    transfers" objection.

WHAT IS NOT COVERED (fundamentally out of reach for our method):
  - Dice-roll seeds (physical entropy) — not brute-forceable.
  - BIP-39 passphrase (external entropy in the KDF) — not recoverable without a
    wordlist.
  - Devices on fixed firmware (4.2.0+ / 5.6.0+) — the RNG is correct.
  - Mk4-specific victims: Mk4 is VULNERABLE (see 2.5), but a direct sha256d scan
    yielded 0 additional hits; such seeds are either indistinguishable from the
    Mk3 set or fall under dice/passphrase. Estimated unreachable population:
    ~700–1,500 seeds.
  - Non-bc1q victims (legacy/P2SH/taproot): ~1,245 victim-list addresses are not
    covered (the brute force checked the bloom filter predominantly for bc1q);
    see 4.7.1.

IMPLICATION FOR INTERPRETATION:
  Net Stolen 5,080 BTC ($399M) is a PROVEN MINIMUM. The real damage may be higher
  due to the unreachable categories above. Gross 10,950 BTC is an upper bound on
  the volume that moved through the compromised keys (with change-cycling). For
  comparison with public reports, use Net (see 7A).

REPRODUCIBILITY AND CHAIN-OF-CUSTODY:
  All key artifacts (the bit-exact Yasmarang algorithm, the UID model, the bloom

================================================================================
2. THE VULNERABILITY
================================================================================

2.1 Root Cause
--------------------------------------------------------------------------------

File:   mpconfigboard_MK3.h (Coldcard Mk3 firmware)
Line:   #define MICROPY_HW_ENABLE_RNG (0)

The C preprocessor macro MICROPY_HW_ENABLE_RNG was set to 0 (disabled) instead of
1 (enabled). In random.c the guard directive:

  #ifndef MICROPY_HW_ENABLE_RNG
    #error "RNG must be configured"
  #endif

...does NOT fire, because the macro IS defined (as 0), and #ifndef only checks
whether it is defined, not its value. As a result the linkage resolves to:

  rng_get() -> pyb_rng_yasmarang()     (software PRNG, ~24 bits)

instead of:

  rng_get() -> RNG->DR                 (STM32 hardware TRNG, 256 bits)

This is a classic silent-misconfiguration bug: the code compiles without errors
or warnings, the device works correctly on the surface, but all key-generation
entropy comes from a predictable software PRNG.

2.2 Effective entropy (19-20 bits instead of 256)
--------------------------------------------------------------------------------

The firmware forms entropy from TWO Yasmarang instances (details in 2.2.1). Below
are the constants of the NGU path (the mixer); the CHIP path has n=d=dat=0 (RTC
disabled, see 2.2.2), and its pad = UNIQUE_ID XOR SysTick->VAL:

  NGU path (mixer, constant across all devices):
    pad:  [REDACTED]   n: [•]   d: [•]   dat: 0   (internal constants withheld)
  CHIP path (the only source of variability):
    pad:  UNIQUE_ID XOR SysTick->VAL   n: 0   d: 0   dat: 0

Nominally pad carries 32 bits. However the effective entropy is only ~19-20 bits
for the following reasons:

  - STM32 device UNIQUE_ID clusters within manufacturing lots (devices from the
    same lot have close values);
  - SysTick->VAL is predictable in narrow time windows (the moment of seed
    generation on first boot / ceremony);
  - the empirically observed PAD distribution is tightly bounded to the range
    0x000F02C9 - 0x004BF595 (~4.5M values instead of 4.3 billion).

Practical search space: ~5.2M PAD x ~298 SKIP ~= 1.56 billion candidates, which
is trivially brute-forced on a GPU.

2.2.1 The Yasmarang algorithm and the two-instance construction
--------------------------------------------------------------------------------

Yasmarang is a compact non-cryptographic PRNG with a 32-bit state word (pad) and
three auxiliary registers (n, d, dat). Its state-transition function, recovered
from the firmware and verified bit-for-bit against a device, is:

  uint32_t yasmarang_next(yasmarang_t *y) {
      y->pad += y->dat + y->d * y->n;
      y->pad = (y->pad << 3) + (y->pad >> 29);   // rotate left by 3
      y->n   = y->pad | 2;
      y->d  ^= (y->pad << 31) + (y->pad >> 1);
      y->dat ^= (y->pad & 0xFF) ^ ((y->d >> 8) & 0xFF) ^ 1;
      return y->pad ^ (y->d << 5) ^ (y->pad >> 18) ^ (y->dat << 1);
  }

It is a decent statistical PRNG (passes diehard-like tests with a random seed),
but it is fully deterministic given its initial state. It has no cryptographic
strength and cannot: given (pad, n, d, dat), the entire future stream is
reproducible.

The Coldcard firmware forms the 32 bytes of seed entropy NOT from one but from
TWO Yasmarang instances, XOR-ed byte-wise (8 iterations of 4 bytes each):

  yasmarang_t chip = { uid ^ systick, RTC->TR, RTC->SSR, 0 };  // "chip path"
  yasmarang_t ngu  = { [REDACTED internal constants] };  // "ngu path"

  for (i = 0; i < 8; i++) {
      uint32_t mixed = yasmarang_next(&chip) ^ yasmarang_next(&ngu);
      // 4 bytes of mixed -> out[4*i .. 4*i+3]
  }
  // then: seed32 = SHA256d(out)  ->  BIP-39 mnemonic

The design intent is to mix a "hardware" source (chip path, where pad is taken
from UNIQUE_ID XOR SysTick) with a "software" ngu path. But because of
MICROPY_HW_ENABLE_RNG=0 the chip path does NOT access the hardware TRNG (RNG->DR)
and is itself a software Yasmarang. So both streams are deterministic PRNGs, and
the XOR of two predictable streams remains predictable.

2.2.2 Entropy collapse: why only ~19-20 bits remain
--------------------------------------------------------------------------------

Consider the actual initial states of both instances on a real Mk3:

  ngu path = { [REDACTED internal constants] }
    ALL four fields are hard-coded constants. Therefore the stream
    yasmarang_next(&ngu) is IDENTICAL on every device and in every run. It is not
    an entropy source but a fixed, known XOR mask.

  chip path = { uid ^ systick, RTC->TR, RTC->SSR, 0 }
    On the Mk3 the macro MICROPY_HW_ENABLE_RTC=0, so the RTC registers are
    uninitialized: RTC->TR = 0 and RTC->SSR = 0. Hence:
      n   = 0
      d   = 0
      dat = 0
      pad = uid ^ systick   <-- THE ONLY variable quantity

Thus all seed entropy reduces to the 32-bit value
pad = UNIQUE_ID_word0 ^ SysTick->VAL. This is fundamental: not 256 bits, not even
32 independent bits, but a single 32-bit number whose effective diversity is
further limited by the properties of both XOR operands (discussed in 2.2.3). This
is exactly why brute force reduces to enumerating a single PAD parameter (plus a
SKIP parameter — the number of PRNG "advances" before the seed is fixed, see 3.7).

2.2.3 The UID model and the STM32L496 entropy budget
--------------------------------------------------------------------------------

The Coldcard Mk3 MCU is an STM32L496RGT6. The 96-bit UNIQUE_ID sits at address
0x1FFF7590. word0 is used to form pad:

  word0 = X[15:0] | Y[31:16]   (die coordinates on the wafer: X, Y)

Empirical analysis of 11 real STM32 UIDs (from open sources: ST forums, GitHub,
techoverflow) revealed a stable structure:

  #   Chip     word0        X    Y     Wafer  Lot
  --  -------  -----------  ---  ----  -----  --------
   1  L476     0x004A0029   41    74     17   P3XK71
   2  F405     0x0025001E   30    37     12   Q319784
   3  F2       0x006C0028   40   108     20   Q819670
   4  L4/G     0x005D004D   77    93      4   P67A00
   5  L4/G     0x00520033   51    82     14   PBTQ99
   6  F042     0x000C0020   32    12      5   042ACC

Observations (N=11):
  - X in [30, 77], Y in [12, 108] — coordinates fit within a single byte;
  - every word0 has the form 0x00YY00XX — the high bytes of each coordinate = 0;
  - effective entropy of word0 ~= 14 bits (X ~7 bits + Y ~7 bits);
  - the UID is NOT secret: it leaks via USB serial and machine.unique_id().

Resulting Mk3 seed entropy budget:

  Component                        Contribution
  -------------------------------  ------------------------------------
  UNIQUE_ID word0 (X,Y)            ~14 bits (clustered by lot)
  SysTick->VAL at generation time  a few bits (narrow time window)
  RTC->TR, RTC->SSR                0 bits (RTC disabled)
  ngu path (constant)              0 bits
  -------------------------------  ------------------------------------
  EFFECTIVELY                      ~19-20 bits

The empirically recovered PAD range (0x000F02C9 - 0x004BF595) and the clustering
by manufacturing lot confirm this estimate: the space of real pad values is
~4.5 million, not 4.3 billion, which makes exhaustive search trivial.

2.5 Mk4 assessment: VULNERABLE (same bug, fixed only in 5.6.0)
--------------------------------------------------------------------------------

IMPORTANT (v4 revision): this section was reworked after a direct audit of the
Mk4 firmware sources (github.com/Coldcard/firmware + the libngu submodule),
conducted in a separate Mk4 phase (5 rounds). The early estimate of "~56 bits,
infeasible" is REFUTED by the source code.

2.5.1 Mk4 shared the same vulnerability
Mk4 firmware 5.0.0 (Mar 2022) - 5.5.1 (Jul 2026) used the SAME Yasmarang PRNG as
the Mk3. The official Coinkite ChangeLog (Security Advisory, July 2026), verbatim:
  "Versions from 2021 to July 2026 had a bug which produced poor entropy."
  "Master seeds can only be trusted from releases after:
     5.6.0 (Mk4, MK5), 4.2.0 (Mk3), 1.5.0Q (Q1), 6.6.0 (Edge)."

2.5.2 The SE reseed was truncated to 32 bits (did not help)
Mk4's design was to reseed Yasmarang from two Secure Elements. But the old
shared/mk4.py::rng_seeding() (before fix ac1644cd, 2026-08-14) contained:

  a = callgate.read_rng(1)          # SE1
  b = callgate.read_rng(2)          # SE2
  n = ngu.hash.sha256d(a+b)
  n, = ustruct.unpack('I', n[0:4])  # <-- TRUNCATION 256 -> 32 bits
  ngu.random.reseed(n)

So a 256-bit SE digest was truncated to 32 bits before the reseed. Moreover, the
seed generation itself (shared/seed.py::generate_seed before fix 493b77c3) did
NOT mix in the SE at all:

  seed = ngu.random.bytes(32)       # Yasmarang only
  return ngu.hash.sha256d(seed)

The real ceiling of the vulnerable Mk4 = 2^32 (reseed truncation), NOT 2^56. This
revision was confirmed after the source code was presented.

2.5.3 Model timeline and fixes (firmware git history)
  generate_seed = sha256s(random.bytes(32))    started 2022 (Mk4 5.0.0)
    -> sha256d(random.bytes(32))  commit 024655be  2024-01-10 (shipped ~5.3.x)
  fix: SE-mixing in seed          commit 493b77c3  2026-08-14 (5.6.0)
  fix: full-256 boot reseed       commit ac1644cd  2026-08-14 (5.6.0)
  libngu: Yasmarang -> SHA-256 Hash-DRBG (NIST SP 800-90A)
                                  commit 36ee40b   2026-08-05
The cryptographic component (libngu) is attached to the firmware as a submodule;
its development/merge of security-critical code without independent review is a
key process factor (see Section 7).

2.5.4 Empirical result of the Mk4 scans
Despite the confirmed vulnerability, GPU scans of the direct sha256d flow of Mk4
(pad 0..2^25, skip 0-32, indices 0-4; ~1.07 billion candidates) produced 0 hits.
Pipeline validation passed (the mini-ceremony model re-discovered a known Mk3
victim, PAD=0x0012563E). Interpretation of the null result:
  - Mk4 victims used the mini-ceremony (the same path as Mk3) and are
    INDISTINGUISHABLE by address from our 2,052 seeds -> some of the 2,052 may in
    fact be Mk4;
  - the direct sha256d flow (2024+ era) either produced no vulnerable seeds in the
    current victim list, or those victims used dice/passphrase (unrecoverable);
  - the uncovered 889 bc1q victims (88% with a first UTXO in 2024+, per
    timeline-forensics) very likely belong to this era and are NOT brute-forceable
    (dice / passphrase / firmware 5.6.0+).

VERDICT (revised): Mk4 is VULNERABLE on all versions before 5.6.0. What "saved" it
was not a correct RNG configuration but only that the truncated reseed yielded
2^32 and mass exploitation focused on the easier Mk3. Practical recovery of
Mk4-specific seeds by our method produced 0 additional hits (victims are
indistinguishable from the Mk3 set or used mitigations) — but the public claim
"Mk4 is not vulnerable" is factually INCORRECT.

2.6 Step-by-step exploit walkthrough
--------------------------------------------------------------------------------

The full path from device boot to a predictable seed on vulnerable Mk3 firmware:

  Step 1. On startup / seed generation, generate_seed() is called
          (firmware_seed.py:605), which requests 32 bytes of entropy:
          seed = ngu.random.bytes(32).

  Step 2. ngu.random.bytes() -> random_bytes() -> my_random_bytes(dest, 32)
          (random.c:68). Internally a byte stream is formed as
          CHIP_TRNG_32() XOR my_yasmarang().

  Step 3. CHIP_TRNG_32() = rng_get(). Because of MICROPY_HW_ENABLE_RNG=0, the
          rng_get() function is linked to pyb_rng_yasmarang(), NOT to RNG->DR.
          Thus BOTH halves of the XOR are software Yasmarang with a predictable
          state (pad = UNIQUE_ID ^ SysTick, n/d/dat fixed). The XOR of two
          predictable streams remains predictable.

  Step 4. The resulting 32 bytes are passed through sha256d and encoded into a
          24-word BIP-39 mnemonic. All seed entropy is determined by the single
          pad value (~19-20 effective bits).

  Step 5. On the way from boot to the moment the seed is fixed, the PRNG is
          "advanced" some number of times (UI navigation, PIN ceremony,
          mini-ceremony). That number is the SKIP parameter and shifts the PRNG
          state. The attacker enumerates (PAD, SKIP) pairs, simulating the same
          call sequence as the firmware.

  Step 6. For each candidate a mnemonic is computed -> BIP84 master key ->
          addresses recv[0..4]. If at least one address is present in the bloom
          (ever used on the Bitcoin network), the candidate is flagged as a likely
          hit and confirmed by full derivation.

It is exactly this determinism (fixed internal constants and a narrow pad
distribution) that turns a nominally-256-bit generation into an enumeration of
~1.56 billion options — a task of minutes on a single GPU. The attacker needs no
physical access to the victim device: it is enough to know the PRNG model and the
pad/SKIP range, after which they generate all possible seeds and match their
addresses against the blockchain.

3.1 GPU Brute-Force (mc24w — Mini Ceremony 24-word)
--------------------------------------------------------------------------------

GPU-accelerated enumeration of the Yasmarang PRNG state:

  - PAD range:  0x000000 - 0x4FFFFF (~5.2M candidates)
  - SKIP range: 3 - 300 (navigation steps during the seed ceremony; a later
                extended pass reached ~1024)
  - For each (PAD, SKIP) pair: simulate the ceremony -> derive the BIP-39
    mnemonic -> compute BIP84 receive addresses (indices 0-4) -> check via the
    bloom filter.

  Hardware: NVIDIA GPU with a custom CUDA BIP32 kernel
  Speed:    ~134,823 candidates/s
  Total:    ~1.56 billion candidates (5.2M PAD x ~298 SKIP)

Ceremony model: mc24w (mini-ceremony) and pc24w (pin-ceremony) — two ways to
launch seed generation on the device, differing in the number of navigation steps
(SKIP) that consume PRNG values before the seed entropy is fixed.

3.7 Ceremony model and GPU-kernel design
--------------------------------------------------------------------------------

The SKIP parameter reflects the number of PRNG calls between reseed and the moment
seed entropy is fixed. The device offers several generation paths that differ in
this number:

  mc24w (mini-ceremony 24-word): a short path, SKIP range 3-300 (later extended
    to ~1024). The main productive vector — produced practically all 2,052 seeds.
  pc24w (pin-ceremony 24-word): a path with PIN entry, parameterized by a
    (PIN-length, NAV-steps) pair. Fully scanned (PIN 1-20, NAV 1-75) — produced no
    new seeds: all pc24w hits reduce to already-known PADs from mc24w.

Empirically the SKIP distribution concentrates in the narrow range 6-295 (with a
single outlier at 502) with a peak at SKIP=12 (108 seeds). The theoretical maximum
is estimated at ~500 (corresponding to ~19 ceremony rejections) — empirically
confirmed by one seed recovered at SKIP=502. A scan of SKIP 301-400 over 524M
candidates gave 0 hits; a subsequent extended scan of SKIP 401-1024 yielded exactly
one further seed (at SKIP=502), showing the tail beyond the main band is extremely
sparse but not strictly empty. SKIP values above ~1024 were not scanned; their
expected yield is negligible.

The CUDA BIP32 kernel is the key performance element:

  - window-8 precomputation for scalar multiplication on the secp256k1 curve;
  - a shared-memory-resident H160 bloom (1.797 GB) for instant hash160 address
    checks directly on the GPU without host round-trips;
  - a multi-index prefilter (indices 0-4) to eliminate the blind spot (cases where
    recv[0] is absent from the bloom snapshot);
  - for deep derivation — generation to depth 10,000 across the recv and change
    branches of accounts 0-4.

Performance: ~134,823 candidates/s in the seed brute-force stage and ~205M
derivations in ~1.8 hours in the deep-10K stage. For comparison, a pure-CPU deep
10K would have taken ~39 hours; moving BIP32 onto the GPU gave roughly a 100x
speedup. The paper-wallet vector (no BIP-39/PBKDF2) reaches ~50M keys/s on GPU —
~370x faster than seed brute force, but 0 hits in the victim list indicate that
paper wallets were either not used by victims or are absent from the current
victim list.


3.8 The address-derivation chain: BIP-39 -> BIP-32 -> BIP-84
--------------------------------------------------------------------------------

A standard deterministic chain leads from the recovered 32-byte entropy value to a
specific bc1q address. Reproducing it exactly is critical: any error in the
derivation path yields different addresses and a false "0 hits".

  Step 1 (BIP-39). Entropy -> mnemonic.
    entropy32 = SHA256d(raw_yasmarang_output)
    24-word mnemonic = encoding (entropy || checksum) via the BIP-39 wordlist
    (2048 words, 11 bits per word). For 256 bits of entropy + 8 checksum bits =
    264 bits = 24 words.

  Step 2 (BIP-39 seed). Mnemonic -> 512-bit seed.
    seed512 = PBKDF2-HMAC-SHA512(mnemonic, "mnemonic" + passphrase, 2048 iters)
    Those 2048 PBKDF2 iterations are the main bottleneck of seed brute force
    (~134K candidates/s). Paper wallets skip this step (no BIP-39), hence their
    ~370x faster enumeration.

  Step 3 (BIP-32). seed512 -> master key.
    (master_priv, master_chaincode) = HMAC-SHA512("Bitcoin seed", seed512)
    Then hierarchical derivation along the path with hardened and normal indices
    via repeated HMAC-SHA512.

  Step 4 (BIP-84 path). For Native SegWit (bc1q):
    m / 84' / 0' / account' / change / index
      84'   = purpose (BIP-84, P2WPKH)
      0'    = coin_type (Bitcoin mainnet)
      account' = account number (0 for 99%+ of victims)
      change   = 0 (receive) or 1 (change)
      index    = 0..N (0..9999 in deep 10K)

  Step 5 (address). pubkey -> address.
    pubkey (33 bytes, compressed) -> HASH160 = RIPEMD160(SHA256(pubkey))
    -> bech32 encoding with witness version 0 -> bc1q...

The GPU-resident H160 bloom operates at the HASH160 level: the kernel computes the
20-byte hash160 directly on the device and checks it in the bloom without a host
round-trip. 48 paths were tested (BIP84/44/49/86/48/bare/BIP45), but effectively
all hits came from BIP84 account 0 (99.2%), confirming the victim profile as
default Native SegWit users.

3.9 Bloom-filter math
--------------------------------------------------------------------------------

A bloom filter is a probabilistic structure giving "definitely no" or "maybe yes".
For forensics the parameter choice is critical: too high an FP produces false hits
(each requiring an expensive full derivation and on-chain check), too large a
filter will not fit in GPU/host memory.

Loyce bloom parameters:
  n (elements)  = 1,571,613,883 addresses
  p (target FP) = 1e-7
  m (array bits)= ceil(-n * ln(p) / (ln 2)^2) ~= 6.75e10 bits ~= 8.39 GB
  k (hashes)    = round((m/n) * ln 2) = 24

Double hashing instead of 24 independent hashes:
  h1, h2 = the two 64-bit halves of MurmurHash3_x64_128(addr)
  for i in [0, k): bit_index = (h1 + i * h2) mod m
  CRITICAL: (h1 + i*h2) is computed in uint64 with overflow masked by
  & 0xFFFFFFFFFFFFFFFF, otherwise the indices diverge from those used at build
  time and produce false misses. This detail was the source of an early bug and is
  recorded as a mandatory implementation rule.

Why this surfaced 3.4x more victims: the original bloom held only addresses with a
balance > 0 (a UTXO snapshot), so ALL drained addresses (balance = 0 but with
history) were invisible. The Loyce bloom contains every address that ever
participated in a transaction — which is exactly the mass of victims whose funds
are already stolen.

The H160 bloom (GPU-resident) is built only on the 421M bc1q addresses and stores
20-byte hash160 values directly, allowing a candidate to be checked on the GPU
without encoding to a bech32 string — a saving on each of the ~205M deep-scan
derivations.

3.10 TX Graph classification algorithm (Net Stolen)
--------------------------------------------------------------------------------

Gross total_received systematically overstates the damage: when a victim spends,
the change returns to a change address of the same seed — and is counted again as
an "inflow". To obtain the net stolen amount, each of the 46,131 transactions is
classified by the composition of its inputs and outputs relative to the set V of
all 35,189 victim addresses.

  For a transaction T define:
    inputs_from_V  = inputs belonging to addresses in V
    outputs_to_V   = outputs going to addresses in V
    external_in    = inputs NOT belonging to V

  Classification:
    INTERNAL  — all inputs from V AND all outputs to V (change/movement within the
                victim's wallet). The volume is NOT counted as stolen.
    EXTERNAL  — inputs from outside V (a real inflow to a victim address). The
                outputs_to_V volume is counted as incoming damage.
    MIXED     — inputs partly from V, partly external. Conservatively counted as
                external (we do not understate the damage).

  Net Stolen = sum of external deposits + mixed deposits.

Result:
  46,131 TX = 9,159 internal + 36,931 external + 41 mixed
  Gross 10,950.75 BTC
    - internal 5,869.83 BTC (53.6%)  <- NOT damage (change cycling)
    - external 5,076.71 BTC (46.4%)  <- real inflows
    - mixed        3.19 BTC          <- counted as external
  NET STOLEN = 5,079.90 BTC

Edge cases and correctness:
  - Transactions with several outputs to V are counted proportionally (only the
    part that landed in V).
  - The attacker's own consolidation transactions (sweeping from many victim
    addresses to its hub) are classified as EXTERNAL from the V-input side: this is
    the moment of actual theft, as funds leave the victim's perimeter.
  - Coverage: 35,189/35,189 addresses (100%), 0 history-collection errors.
  The final figure 5,079.90 BTC is derived from the full graph and is not subject
  to the "these are internal transfers" objection.


3.11 Balance-verification and forensic-collection pipeline

Reaching 100% balance coverage for 35,189 addresses required a multi-pass pipeline
combining several data sources, since no single source gave a complete and correct
result. Below are the passes and the systematic errors found along the way, whose
correction materially affected the final figures.

Pass 1 — Electrum forensic (SSL). The main source: a direct SSL connection to
Electrum servers requesting the full transaction history by each address's
scripthash. Covered 18,071 addresses with full TX and balance data. This pass also

Pass 2 — REST API (blockstream.info, blockchain.info, btcscan.org). Used as a fast

Pass 3 — Electrum total_received (raw TX parsing). For addresses where the

addresses.

Pass 4 — pending sweep. A final top-up of 445 addresses not covered by earlier
passes, via a combination of Electrum + REST fallback.

Pass 5 — Zero-BTC fix. A CRITICAL pass. It was found that early queries via some
Electrum endpoints returned a balance of 0 for addresses that in fact had a

understated the total estimate. Re-parsing raw transactions for 5,849 affected

Coverage summary:

  ------------------------------------------------------

All 35,189 addresses have DRAINED status (balance 0, TX > 0). Active balances: 0.

4.4 What the 53.6% internal ratio means
--------------------------------------------------------------------------------

53.6% of the total volume (5,869.83 BTC) is internal transfers between addresses of
the same victims (change outputs during ordinary spends: the user sent funds to
their own automatically generated change address of the same seed). These amounts
are NOT stolen — it is the same bitcoin circulating inside the victim's wallet,
counted repeatedly in Gross.

The remaining 46.4% (5,076.71 BTC external + 3.19 BTC mixed = 5,079.90 BTC) are
real external inflows to the compromised addresses that were ultimately stolen.
This is a mathematically rock-solid net-damage figure, computed from the full
transaction graph (100% coverage) and not subject to the "these are internal
transfers" objection.

Definitions for use in communication:
  Gross Compromised Volume (10,950 BTC / $861M) — the total volume that passed
    through the compromised keys; shows the SCALE of the vulnerability's reach.
  Net Stolen (5,080 BTC / $399M) — the ACTUAL damage; an incontestable metric.

The forecast (internal ratio would rise to 60-65% at 100% coverage) did not hold:
actual internal was 53.6%, i.e. the net damage came out HIGHER than forecast.

4.5 Cross-chain $0: confirmation of a Bitcoin-only victim profile
--------------------------------------------------------------------------------

A null result across all 11 chains (123,060 addresses) proves that Coldcard Mk3
victims did not import their seeds into multi-currency wallets (MetaMask, Trust
Wallet, etc.) and used the device strictly as intended — as Bitcoin-only cold
storage. This indirectly confirms that a multi-address (BIP44/49/86) rescan has low

4.6 Entropy reconciliation: 2^40.69 (BlockSec) vs 2^19-20 (our audit)
--------------------------------------------------------------------------------

BlockSec estimated the Mk3 ceiling at 2^40.69. This is not an error but a different
point of measurement. The discrepancy comes from WHAT is being modeled:

  BlockSec (2^40.69):
    Models the Yasmarang PRNG state space — the combinatorics of all reachable
    internal states as inputs vary. This is an upper theoretical bound if the
    32-bit pad plus the accompanying registers were independently random.

  Our audit (2^19-20):
    Measures the INPUT entropy actually available to the device. As shown in
    2.2.2-2.2.3, the chip path on the Mk3 has n=d=dat=0 (RTC disabled), the ngu
    path is a constant, and the only variable is pad = UID_word0 ^ SysTick. word0
    carries ~14 bits (die coordinates X,Y, one byte each), SysTick adds a few bits
    in a narrow time window.

Key to the discrepancy: the PRNG state space may be large, but if only ~19-20 bits
of entropy are fed in, only ~2^20 distinct output streams are reachable. The other
"states" from the 2^40.69 estimate are unreachable because the corresponding inputs
never occur on real hardware. Empirical confirmation — the observed PAD range
(0x000F02C9 - 0x004BF595, ~4.5M values) and the successful recovery of 2,052 seeds
by enumerating ~1.56 billion candidates (PAD x SKIP).

Practical conclusion: Coinkite's official wording ("~72 bits of entropy instead of
128") understates the severity by orders of magnitude. The real effective entropy
of ~19-20 bits makes the attack not "theoretically weakened" but trivially
executable on a single GPU in minutes.

4.7.1 The non-bc1q address gap (method limitation)
--------------------------------------------------------------------------------

A separate limitation concerns address types. Our prefilter checked the bloom
predominantly for bc1q (BIP84), so victims who funded ONLY legacy (1...), P2SH
(3...) or taproot (bc1p) were not detected during brute force. In the 6,541 victim
list:

  Type            Recovered   Total in victim list   Coverage
  --------------  ---------   --------------------   --------
  bc1q (BIP84)    4,394       5,283                  83.2%
  legacy (BIP44)  11          777                    1.4%
  P2SH (BIP49)    2           295                    0.7%
  taproot (BIP86) 0           186                    0.0%

Verification (deriving all 2,052 seeds across 48 paths x depth 10,000): 0 of 1,245
non-bc1q victim addresses derive from our seeds. Hypothesis: ~1,245 non-bc1q
victims = SEPARATE unfound seeds (their owners did not fund bc1q, so the bc1q bloom
missed them). To test this, an all-types h160 bloom was built (1,421,683,820
hashes: bc1q+legacy+P2SH; all 1,072 legacy/P2SH victim addresses are in it) and a
mini-ceremony brute-force scan was run (pad 0..0x600000, shuffle 3-300, multi-
address prefilter BIP84+BIP49+BIP44), covering the entire empirical PAD range.

Gap B RESULT (FINAL): 2,051 hits, of which 2,042 = already-known Mk3 seeds
(re-discovery), 9 "new". Deep derivation of those 9 (48 paths x 10,000 depth, an
independent h160 bloom) gave 0 victim and 0 bloom matches, and their match
addresses are ABSENT from the victim list -> the 9 "new" = BLOOM FALSE POSITIVES
(loyce string bloom, FP ~1e-7). Conclusion: Gap B = 0 confirmed new victims.

CONCLUSION: the forecast (+300-400 seeds) did not hold. Non-bc1q victim addresses
are NOT recovered by new mini-ceremony seeds — therefore they belong either to the
same 2,052 seeds (via non-standard paths) or to seeds with a BIP-39 passphrase /
dice entropy, which are mathematically unrecoverable. For completeness the upper
pad range 0x600000..0x1000000 was also scanned (3,124,756,480 candidates, same
model): 0 hits. Thus the entire pad range 0..2^24 is covered with zero gain in real
victims. Recovery of the population vulnerable to the Yasmarang bug is
substantially complete at 2,052 seeds (~99% of the ~2,070 estimate). An
extended-shuffle scan (SKIP up to ~1024) recovered one further seed at SKIP=502 —
empirically confirming the ~500 theoretical maximum — and no others; the tail
beyond the main SKIP band is thin but not strictly empty, and SKIP values above
~1024 remain unscanned with an expected negligible yield. Taproot (32-byte x-only,
BIP341) remains the
only unchecked type; its expected contribution is negligible (186 of 6,541 victim =
2.8%, with a null result across the other types).

4.8 Cross-chain derivation: technical detail of the null result
--------------------------------------------------------------------------------

The null cross-chain result is not an absence of checking but the outcome of
exhaustive derivation across each target chain's algorithms. The same 512-bit
BIP-39 seed produces valid addresses on any blockchain using standard HD
derivation; had victims imported the seed into multi-currency wallets, funds on
those chains would be equally vulnerable and probably already stolen. Checking each
chain requires exact reproduction of its derivation scheme:

  EVM family (ETH, BSC, Polygon, Avalanche, Arbitrum, Optimism, Base):
    A single path m/44'/60'/0'/0/N (secp256k1). Public key (uncompressed, no
    prefix) -> Keccak256 -> low 20 bytes -> 0x... address. The same private key is
    valid on ALL EVM chains, so one derivation covers the whole family; token
    checks (ERC-20: USDT, USDC) are done in addition to the native balance.

  UTXO secp256k1 family:
    LTC   m/44'/2'/0'/0/N   -> P2PKH/bech32 (L.../ltc1...)
    BCH   m/44'/145'/0'/0/N -> CashAddr (q.../legacy 1...)
    DOGE  m/44'/3'/0'/0/N   -> P2PKH (D...)
    DASH/ZEC (transparent)  -> via Blockchair API
    The only difference from Bitcoin is version bytes and encoding; the curve and
    derivation are identical.

  TRX (Tron): m/44'/195'/0'/0/N, secp256k1 + Keccak256 + prefix 0x41 -> base58check
    (T...). Native TRX and TRC-20 (USDT) checked.

  SOL (Solana): m/44'/501'/N', ED25519 curve (NOT secp256k1). Requires a separate
    ED25519-HD derivation from the same 512-bit seed; address = base58 of the
    public key.

  XRP, ATOM: checked via the respective RPC/LCD.
  XMR (Monero): excluded — non-standard EdDSA derivation, not derivable from a
    BIP-39 seed without Monero-specific tooling.

Result: 123,060 addresses across 11 chains, 0 hits, $0. This positively proves the
Bitcoin-only victim profile of Coldcard users (the device was used strictly as BTC
cold storage) and withdraws the earlier "$500M+ with cross-chain assets"
hypothesis. The damage is exclusively in BTC.

5.5 A statistical model of bot behavior
--------------------------------------------------------------------------------

The profile of the 202 waves and the drain-delay distribution allow the operational
model of the early operator (Phase 1) to be reconstructed as an automated bot
rather than a series of manual thefts:

  1. CONTINUOUS MONITORING. Median delay from funding to draining is 653 days, with
     47.1% of addresses drained 2+ years later. A manual operator would not track
     thousands of addresses for years; this is scanner behavior, continuously
     matching the blockchain against a pre-generated set of compromised seeds.

  2. BALANCE THRESHOLD. The spread of amounts per wave (from 0.01 to 78 BTC) and the
     fact that a drain often follows soon after a large inflow are consistent with a
     rule of "drain when funds arrive above a threshold", sweeping up small remnants
     in bulk consolidation waves.

  3. REGULARITY, NOT RANDOMNESS. The waves span the entire 2021-2026 period with a
     peak in 2022 (matching the sales peak of vulnerable Mk3s). The monthly curve of
     newly drained addresses is a proxy for the vulnerability window: growth in
     2021-2022, decline after ~2023 (release of patch 4.2.0).

  4. DELAYED CONSOLIDATION. The early bot held 51.07 BTC for two years and
     consolidated into the hub only 3 months before the public waves (2026-04-27).
     This is "accumulator" behavior, confident in the vulnerability's invisibility,
     not a hurried opportunist rushing to cash out.

  5. PHASE TRANSITION AT DISCLOSURE. The 201 waves of Phase 1 (slow bleeding) are
     followed by a single giant Wave 202 (6,354 addresses, 1,667 BTC in ~3 days)
     immediately after public disclosure on 2026-07-30. The sharp change of pattern
     (mass of addresses, spraying across hundreds of new addresses instead of a
     single hub, "sweep rate 45x baseline") indicates the arrival of many copycats
     (15-25+ by TRM/Galaxy estimates) in a "gold-rush" mode over the shared keyspace.

Practical tracing takeaway: Phase 1 is attributed to 1-2 actors with stable
infrastructure (bot -> hub bc1qc779m8...7ueyn), whereas Phase 2 is many independent
operators; they should be separated during clustering and hand-off to LE.

5A.1 Who knew what, and when

Between the release of the bug (March 2021) and public disclosure (July 2026)
~5.3 years elapsed. Our early bot exploited the vulnerability from April 2024 — at
least 27 months before victims learned of it. The external report (~mid-2025) gave
Coinkite an opportunity to close the vulnerability at least a year before the mass
sweep; the rejection of that report is a central element of the responsibility
assessment (Section 7).

5A.2 Coinkite response chronology (July 30-31, 2026)
--------------------------------------------------------------------------------

After the mass sweep began, the manufacturer's response unfolded over ~36 hours:

  Jul 30 22:50 UTC  Coinkite advisory (initially Mk3 only)
  Jul 31 01:49 UTC  Block Engineering: independent root cause analysis
  Jul 31 06:46 UTC  Coinkite expanded scope: Mk4, Mk5, Q also vulnerable
  Jul 31 13:43 UTC  Firmware 4.2.0 (Mk3 patch)
  Jul 31 15:42 UTC  CEO Rodolfo Novak: "We take full accountability"
  Jul 31 16:39 UTC  Coinkite: "~72 bits of entropy instead of 128"

Two aspects of this response deserve criticism. First, initially limiting the scope
to the Mk3 was premature — within hours Mk4/Mk5/Q had to be acknowledged as
affected (although, as our analysis shows, Mk4 does not yield to practical brute
force thanks to the SE reseed). Second, the public "~72 bits" estimate understates
the severity by orders of magnitude: the actual effective Mk3 entropy was ~19-20
bits (Sections 2.2, 4.6). The difference between 72 and 20 bits is the difference
between "theoretically weakened but practically resistant" and "trivially
 hackable on a single GPU in minutes".

5A.3 The patch and post-hotfix bricking
--------------------------------------------------------------------------------

The 4.2.0 patch (for Mk3, released July 31, 2026) fixes the root cause, including
enabling the hardware TRNG. Separately, a post-hotfix bricking incident is noted,
related to subsequent changes (PR #693, merged August 5, 2026): some devices
temporarily failed to boot after the update.

Our assessment: this is a transient DoS (temporary denial of service), NOT
permanent device damage. Devices recover; this behavior is not equivalent to key
loss and should not be conflated with the core RNG vulnerability. Nevertheless,
Coinkite's messaging around this incident should be clarified to avoid provoking
panic among users whose devices were not compromised (e.g. passphrase or dice-roll
users).

5A.4 Affected and unaffected products — clarification
--------------------------------------------------------------------------------

It is important to clearly delineate the perimeter so users do not make false
decisions:

  - TAPSIGNER, OPENDIME, SATSCARD: separate code bases, NOT affected.
  - BIP-39 passphrase users: the base seed is predictable, but the passphrase adds
    external entropy in PBKDF2, so the resulting keys were NOT stolen. However such
    an address could appear in the victim list if it featured in a sweep
    transaction (a false-positive inclusion).
  - Dice-roll users: entropy from a physical source, the seed is NOT predictable,
    funds are safe.
  - Mk1/Mk2 before v4.0.0: outside the regression, NOT affected.

6.10 Forward tracing + haircut taint (how much stolen SITS vs CASHED OUT)
--------------------------------------------------------------------------------

The key question for LE: how much stolen is still on-chain (freezable) and how much
reached exchanges. The answer requires tracing FORWARD from each victim address
through several hops to a terminal.

Forward crawl: 35,189 victims -> 5 hops forward along outgoing transactions.
  - 39,202 nodes, 3.81M edges
  - Terminals: HOLDING (balance > 0.001 BTC = sitting), SERVICE (>800 tx =
    exchange/service = cash-out point), DEADEND, MAXHOP
  - 2,783 SERVICE endpoints (exchanges/services, including targeted expansion)
  - Value-weighted (follow the largest flows), cap TOP_K=8000/hop by BTC volume
    with logging of what was truncated (the "no silent caps" principle)

PROBLEM of naive tracing: attributing the ENTIRE balance of a downstream address to
the flow yields absurdity. Exchange cold wallets (55,000 and 36,000 BTC of other
people's funds) landed in "holding" -> a total of 292,841 BTC, physically impossible
(the whole gross perimeter = 10,950 BTC).

SOLUTION — HAIRCUT TAINT: the stolen share flows along edges, DILUTED at every mix.
At each node the tainted share of what it received is split across its outputs in
proportion to value; the share that settles into the balance = PARKED here; the
share that reaches SERVICE = cashed out. Exchange balances are NOT counted as
stolen — only the part of the tainted flow that actually entered them.

Model check: bc1qx76cae... (balance 398 BTC, Tier-2 cold storage, source — hub
bc1qc779m8) -> haircut counted 360 BTC as stolen (light dilution). bc1qm34lsc...
(balance 11,282 BTC, tx=0) -> only 58 BTC of tainted flow counted, the other 11,224
BTC = other people's money, NOT attributed.

6.10.1 Targeted expansion (reducing uncertainty)
The TOP_K cap left ~1,614 BTC of taint on un-expanded nodes ("unresolved"). Targeted
expansion was implemented: nodes with taint >= 0.02 BTC were expanded, the graph was
augmented, taint recomputed. 2 rounds:
  Base (haircut):      parked 2,512 / service 936 / unresolved 1,614
  Round 1 (+5,858 nd): parked 2,809 / service 979 / unresolved 1,058
  Round 2:             parked 2,918 / service 991 / unresolved  797
The parked increment decays (+297 -> +108), fees rise -> convergence reached.

FINAL DISTRIBUTION (conservation: seeded 5,444.90 BTC ≈ Net Stolen 5,080):
 ┌───────────────────────────────────────────────┬──────────┬───────┐
 │ Bucket                                        │      BTC │   USD │
 ├───────────────────────────────────────────────┼──────────┼───────┤
 │ PARKED (stolen sitting on-chain, freezable)   │ 2,917.83 │ $229M │
 │ Reached SERVICE (cashed out to exchanges)     │   991.34 │  $78M │

================================================================================
7. ROOT CAUSE
================================================================================

7.1 Classification of the bug
--------------------------------------------------------------------------------

The root bug (a build flag that disabled the hardware TRNG in the seed-generation
path) is technically a composition error — an unintended configuration mistake, not
a deliberately planted backdoor. There is no evidence of an intentional backdoor.

7.2 Architectural / process factors (technical facts)
--------------------------------------------------------------------------------

  1. Security-critical crypto code (the entropy generator) was developed and merged
     without independent external review — a violation of Separation of Duties (the
     code author should not be its sole reviewer).
  2. The vulnerability stayed in open source for ~5 years, unfound by the white-hat
     community. A convoluted call chain hid it from public audit.
  3. 27+ months of pre-disclosure exploitation are documented (by on-chain block
     timestamps).

7.3 On personal attribution
--------------------------------------------------------------------------------

This report does NOT advance or confirm personal attribution of responsibility for
the bug. Establishing specific individuals, their roles, and the legal

7A.2 Why public estimates are systematically lower
--------------------------------------------------------------------------------

Three structural factors explain the gap:

  1. TIME WINDOW. Galaxy and BlockSec analyzed the visible post-disclosure waves
     (July-August 2026). They saw the tip of the iceberg — the final
     mass sweep. Our seed-recovery exposed 5.3 years of hidden, slow exploitation
     (March 2021 - August 2026), including the 201 Phase-1 waves invisible at the
     moment of public disclosure.

  2. INCOMPLETE VICTIM LIST. Public lists were built from addresses reported by
     victims themselves, or addresses that appeared in sweep TXs. The 6,541-address
     list covers only ~18.6% of the real perimeter. Change addresses, high-index
     (1001-10000) receive addresses, and additional-account addresses did not make
     it into these lists. Our deep derivation to index 10,000 recovered all 35,189
     addresses of our seed set.

  3. GROSS vs NET. Our Gross (10,950 BTC) is deliberately an upper bound on the
     volume that passed through the compromised keys, including change-cycling.
     Direct comparison of public estimates should be against our Net (5,080 BTC) —
     the actual-damage metric, cleaned of internal transfers via the full TX graph.

8. RECOMMENDATIONS
================================================================================

8.1 For those affected (migration guide)
--------------------------------------------------------------------------------

  1. Check whether the device ran firmware 4.0.1 - 4.1.9.
  2. If so — ALL seeds generated on that device are compromised, including paper
     wallets.
  3. Generate a new seed on a fixed device (firmware 4.2.0+), IDEALLY using
     dice-roll entropy or a BIP-39 passphrase.
  4. Move ALL funds to the new wallet immediately — even if the funds are not yet
     stolen, the attacker may keep monitoring.
  5. Do not rely on a BIP-39 passphrase as the sole protection of the old seed: the
     passphrase adds entropy, but the base seed remains predictable.
  6. CRITICAL WARNING: do NOT fund the old addresses with any amount. An ACTIVE
     automated sweeper bot is attached to the victim addresses (last sweep
     2026-08-19, 460 same-block sweeps documented): any new deposit will be stolen
     within seconds-to-minutes. This is not a residual risk but live infrastructure
     (see 6.11).

8.2 For Law Enforcement
--------------------------------------------------------------------------------

  1. The full list of 35,189 victim addresses (Appendix F) + the consolidation
     addresses (Section 6) for requests to CEXes/providers.
  2. Priority forward tracing of the hub bc1qc779m8...7ueyn (398.49 BTC, 492 TX) to
     CEX deposits.
  3. Subpoena to the blockchain provider where the Wave-1 attacker had a "paid
     account" (KYC data).
  4. Check the P2SH address 3LY6WfeqPSguVH56T8ndJE8VduDkDtuQMo (2022) to establish
     the bot's start date.
  5. Top-20 hubs + P2SH 2022 trace + graph of the first 3 waves — can be started
     immediately with 52.5% of the data, without waiting for full clustering.
  6. FREEZE PARKED funds: haircut tracing (Section 6.10) isolates ~2,918 BTC ($229M)
     of stolen funds still sitting on identified addresses (parked_stolen_wallets.csv,
     1,333 addresses). A priority for seizure/freeze before cash-out. ~991 BTC
     ($78M) already reached SERVICE endpoints (2,783 exchange/service addresses) —
     subpoena this list.
  7. ACTIVE THREAT: the sweeper bot operates to this day. Law enforcement and
     exchanges are advised to warn users about the risk of new inflows to these
     addresses and to account for the bot's activity when coordinating a response.

8.3 For the industry (lessons learned)
--------------------------------------------------------------------------------

  1. The hardware RNG must be enabled by default; disabling it should be impossible
     without an explicit #error.
  2. Preprocessor mistakes of the form #define X (0) vs #define X (1) are a class of
     silent misconfiguration bugs; compilers should warn, and critical macros should
     be checked by value (#if X != 1), not by definition (#ifndef).
  3. Separation of Duties for cryptographic code: the author cannot be the sole
     reviewer; pseudonyms in security-critical contributions are unacceptable.
  4. A bloom filter based on ALL historical addresses (not just current balances) is
     critical for forensic completeness — a balance snapshot hides drained victim
     addresses.
  5. Deep address derivation (>1000 indices) is necessary to capture change
     addresses and high-index usage patterns.

8.4 Early warning on new inflows (for exchanges and coordinators)
--------------------------------------------------------------------------------

Because the attacker's sweeper bot remains active, any new inflow to the 35,189
addresses will be stolen immediately. Industry organizations (exchanges, blockchain-
analytics firms, law enforcement) are technically able to set up early warning of
inflows (e.g. subscribing to the addresses via Electrum). This is an industry-level
recommendation; the author of this report conducts no such monitoring and performs no
transactions with the addresses.

APPENDIX G — GLOSSARY OF TECHNICAL TERMS
--------------------------------------------------------------------------------

  BIP-32       Hierarchical deterministic key derivation (HD wallet). From a single
               master key a tree of child keys is derived.
  BIP-39       Mnemonic-phrase standard. Entropy -> word list (12/24) -> 512-bit
               seed via PBKDF2-HMAC-SHA512 (2048 iterations).
  BIP-44/49/84/86  Derivation-path standards for different address types:
               44 = legacy (1...), 49 = P2SH-SegWit (3...),
               84 = Native SegWit / P2WPKH (bc1q...), 86 = Taproot (bc1p...).
  Bloom filter A probabilistic set-membership structure. Gives "definitely no" or
               "maybe yes" (with a controllable FP rate).
  Change addr  An address to which the wallet returns change when spending a UTXO.
               Generated automatically on the change=1 branch of the same seed.
  DRAINED      Address status: current balance 0 with transaction history (funds
               came in and were withdrawn).
  Entropy      A measure of unpredictability. An ideal seed = 256 bits; the
               vulnerable Mk3 = ~19-20 effective bits.
  External deposit  An inflow to a victim address from outside the perimeter V. In
               the TX-graph classification it is counted as real (stolen) volume.
  FP rate      False-positive rate — the fraction of false bloom-filter matches.
  Gross        Total total_received across all addresses, including internal
               transfers (an upper bound on volume).
  H160 / hash160  RIPEMD160(SHA256(pubkey)) — the 20-byte hash at the core of an
               address.
  Internal transfer  A transfer between addresses of one perimeter (change
               cycling). Not stolen volume.
  KDF          Key Derivation Function (here PBKDF2-HMAC-SHA512).
  mc24w        Mini-ceremony 24-word: a seed-generation path on the device, the main
               productive brute-force vector.
  Net Stolen   Net stolen volume = external + mixed deposits (Gross minus internal
               transfers).
  PAD          The 32-bit Yasmarang state word; on the Mk3 = UID ^ SysTick, the only
               variable quantity of seed entropy.
  pc24w        Pin-ceremony 24-word: a generation path with PIN entry. Fully
               scanned, produced no new seeds.
  PRNG         Pseudo-Random Number Generator (software, deterministic).
  P2WPKH       Pay-to-Witness-Public-Key-Hash — Native SegWit (bc1q).
  SE           Secure Element (ATECC608B / DS28C36B). On the Mk4 it adds a reseed.
  SKIP         The number of PRNG advances from reseed to seed-entropy fixing; the
               second brute-force parameter alongside PAD.
  sha256d      Double SHA-256: SHA256(SHA256(x)).
  SysTick      ARM Cortex-M system timer; SysTick->VAL is used in pad.
  TRNG         True Random Number Generator (hardware, RNG->DR). This is what the
               MICROPY_HW_ENABLE_RNG=0 bug disabled.
  UID / UNIQUE_ID  96-bit STM32 factory identifier; word0 carries ~14 bits of
               entropy (die coordinates X,Y).
  Yasmarang    A compact non-cryptographic PRNG used instead of the hardware TRNG
               due to a configuration error.

APPENDIX H — REPRODUCIBILITY AND LIMITATIONS
--------------------------------------------------------------------------------

Reproducibility. All key artifacts are retained and allow independent verification:
  - The Yasmarang algorithm and entropy model are verified bit-for-bit against a
    device (sha256d_verification/yasmarang_entropy_fixed.c).
  - The UID model is based on empirical data from N=11 real STM32 UIDs from open
    sources (uid_model/uid_analysis.py).
  - The bloom filter is fully documented (Appendix E), including the m/k parameters
    and the uint64-masking rule for double hashing.
  - The TX-graph result is serialized to JSON (tx_graph_gap_results.json) with a
    per-item internal/external/mixed breakdown across 46,131 transactions.
  - The full list of 35,189 addresses is available for on-chain verification.

Limitations and open questions:
  1. The paper-wallet vector gave 0 hits in the victim list; this may reflect either
     an absence of affected paper wallets or the incompleteness of the victim list.
     There is no definite conclusion.
  2. The shared/ modules of the full firmware (USB encrypt, key teleport, web2fa,
     secure notes, seed XOR, cloning ECDH) were not available for audit;
     theoretically they may use the same vulnerable PRNG.
  3. The 2022 P2SH address (3LY6Wfeq...) requires separate tracing to definitively
     confirm the bot's start date.
  4. Attribution of Phase-2 actors (15-25+ copycats) was not performed — this is a
     task for LE using subpoena power over CEXes/providers.
  5. The estimate of the unreachable population (Mk4/dice/passphrase, ~700-1500
     seeds) is a range and is not precisely measurable by our method.

Ethical boundaries. The recovered mnemonics and private keys are not published and
not shared with anyone except authorized recipients (LE / forensic partners). Since
all 35,189 addresses are already drained (balance 0), recovering the seeds created
no new risk for victims. The author does not monitor these addresses and performs no
transactions with them; this report is strictly research and advisory in nature.
