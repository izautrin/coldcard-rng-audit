## TL;DR

An RNG misconfiguration in a batch of Coldcard firmware (`MICROPY_HW_ENABLE_RNG=0`)
caused seed phrases to be generated by a **software pseudo-random generator**
instead of the hardware TRNG. Effective key entropy collapsed from 256 bits to
roughly **19–20 bits** — a range that is brute-forceable on a single consumer GPU.

Independent on-chain analysis reconstructed the scope of the resulting theft.

## The vulnerability (technical, high level)

- A build flag disabled the hardware TRNG path for the seed-generation routine.
- Seeds were derived from a small-state software PRNG (Yasmarang-family), whose
  effective entropy in the affected path is ~19–20 bits.
- With so little entropy, the full key space is enumerable on commodity GPUs in
  minutes-to-hours, letting an attacker regenerate victims' seeds and derive their
  addresses.
- The flaw affected the *entropy source*, not the elliptic-curve/derivation math;
  standard BIP-39/BIP-32/BIP-84 wallets built on these seeds were fully derivable.

This class of issue was also noted publicly by third parties (e.g. Galaxy Research,
BlockSec). This repository is an **independent** reconstruction that arrives at a
substantially larger scope by (a) exhaustively recovering the seed population and
(b) tracing change/deep-derivation addresses that address-list-only studies miss.

## Scope & method (high level)

- GPU brute-force recovery of the vulnerable seed population up to its practical ceiling.
- Address derivation across standard paths and depth to enumerate victim addresses.
- On-chain balance + transaction-graph forensics (100% address coverage) to separate
  **internal change-cycling** from **external deposits** and compute *Net stolen*.
- Consolidation-hub mapping and multi-hop "follow-the-money" tracing with a
  **haircut-taint** model to estimate how much stolen BTC is still parked on-chain
  vs. cashed out through services.

Full methodology and derived datasets are shared **privately** with law-enforcement
and blockchain-forensic partners on request.

## For affected users

1. If your device ran Mk3 `4.0.1–4.1.9` or Mk4 `5.0.0–5.5.1`, treat **every** seed
   generated on it as compromised (including paper wallets).
2. Generate a new seed on patched firmware (**4.2.0+ / 5.6.0+**), ideally with
   dice-roll entropy and/or a BIP-39 passphrase.
3. Move funds to the new wallet immediately.
4. **Do not send any amount to old addresses.** On-chain evidence indicates an
   automated sweeper still monitors the affected addresses; new deposits are at risk.

## Responsible-disclosure notice — what is **NOT** in this repo

To avoid enabling copycat attacks on not-yet-recovered wallets and to avoid harm:

- ❌ No recovered seed phrases, PAD/SKIP values, or PRNG constants.
- ❌ No brute-force implementation or exact search parameters.
- ❌ No parked-fund "stolen-wallet" attribution list (haircut tracing has false
  positives — publicly branding an address as holding stolen funds could wrongly
  implicate an innocent holder; that data goes to LE only).
- ❌ **No attribution of blame to any named individual.** Root-cause and any
  personal attribution are questions for independent verification and the proper
  authorities — not for this writeup.

The full evidentiary package (transaction graphs, taint analysis, chain-of-custody
manifest) is provided to law enforcement / forensic firms on request.
