Настоящий документ является defensive security audit — оборонительным
криптографическим расследованием уязвимости генератора случайных чисел
(RNG) в аппаратном кошельке Coldcard Mk3 производства компании Coinkite Inc.

Все работы по восстановлению seed-фраз проводились в исследовательских целях
для определения полного масштаба уже свершившейся кражи. Восстановленные
мнемоники и приватные ключи НЕ публикуются и НЕ включены в этот документ.
Средства на всех идентифицированных адресах уже похищены атакующим (баланс
= 0 на 100% адресов); восстановление seed'ов не создало нового риска для
жертв, но позволило вскрыть полную картину инцидента, недоступную публичным
аналитикам.

Данный отчёт предназначен для передачи в правоохранительные органы (LE),
блокчейн-форензик компаниям (Chainalysis, TRM Labs), а также для
координации с биржами (CEX) по мониторингу адресов консолидации.

Все адреса инфраструктуры атакующего (боты, хабы консолидации, миксеры)
приведены полностью, поскольку они уже публичны и их раскрытие служит целям
расследования. Адреса жертв в теле отчёта приводятся усечённо; полный
список из 35,189 адресов передаётся отдельным приложением.

1.4 Вердикт
--------------------------------------------------------------------------------

Технически корневой баг является composition error — непреднамеренной
ошибкой конфигурации (сборочный флаг, отключивший аппаратный TRNG в пути
генерации seed), а не заведомо внедрённым бэкдором. Доказательств намеренного
бэкдора нет.

Процессные факторы, усугубившие ситуацию (технические факты):
  1. Security-critical криптокод (генератор энтропии) разрабатывался и
     мержился без независимого external review — нарушение принципа
     Separation of Duties.
  2. Уязвимость оставалась в открытом коде ~5 лет, не найденная white-hat
     сообществом; запутанная цепочка вызовов скрывала её от аудита.
  3. 27 месяцев документированной pre-disclosure эксплуатации.

ДИСКЛЕЙМЕР: настоящий документ фиксирует ТЕХНИЧЕСКИЕ факты (баг, энтропия,
масштаб, timeline). Персональная атрибуция ответственности и правовая
квалификация — вне рамок этого отчёта; это задача независимой верификации

2. УЯЗВИМОСТЬ
================================================================================

2.1 Корневая причина (Root Cause)
--------------------------------------------------------------------------------

Файл:   mpconfigboard_MK3.h (прошивка Coldcard Mk3)
Строка: #define MICROPY_HW_ENABLE_RNG (0)

Макрос препроцессора C MICROPY_HW_ENABLE_RNG был установлен в 0 (выключено)
вместо 1 (включено). В файле random.c защитная директива:

  #ifndef MICROPY_HW_ENABLE_RNG
    #error "RNG must be configured"
  #endif

...НЕ срабатывает, потому что макрос ОПРЕДЕЛЁН (как 0), а #ifndef проверяет
лишь факт определения, а не значение. В результате компоновка происходит
так:

  rng_get() -> pyb_rng_yasmarang()     (программный PRNG, ~24 бита)

вместо:

  rng_get() -> RNG->DR                 (аппаратный TRNG STM32, 256 бит)

Это классический пример silent misconfiguration bug: код компилируется без
ошибок и предупреждений, устройство работает внешне корректно, но вся
энтропия генерации ключей исходит из предсказуемого программного PRNG.

2.2 Эффективная энтропия (19-20 бит вместо 256)
--------------------------------------------------------------------------------

Прошивка формирует энтропию из ДВУХ инстансов Yasmarang (детально в 2.2.1).
Ниже приведены константы NGU-пути (микшера); CHIP-путь имеет n=d=dat=0 (RTC
отключён, см. 2.2.2), а его pad = UNIQUE_ID XOR SysTick->VAL:

  NGU-путь (микшер, константа на всех устройствах):
    pad:  [REDACTED]   n: [•]   d: [•]   dat: 0   (внутренние константы withheld)
  CHIP-путь (единственный источник переменности):
    pad:  UNIQUE_ID XOR SysTick->VAL   n: 0   d: 0   dat: 0

Номинально pad несёт 32 бита. Однако эффективная энтропия составляет лишь
~19-20 бит по следующим причинам:

  - UNIQUE_ID устройств STM32 кластеризуется в пределах производственных
    партий (близкие значения у устройств из одной партии);
  - SysTick->VAL предсказуем в узких временных окнах (момент генерации
    seed при первой загрузке / ceremony);
  - эмпирически наблюдаемое распределение PAD жёстко ограничено диапазоном
    0x000F02C9 — 0x004BF595 (~4.5M значений вместо 4.3 млрд).

Практическое пространство поиска: ~5.2M PAD x ~298 SKIP ~= 1.56 млрд
кандидатов, что тривиально перебирается на GPU.

2.2.1 Алгоритм Yasmarang и двухинстансовая конструкция
--------------------------------------------------------------------------------

Yasmarang — компактный некриптографический PRNG с 32-битным словом
состояния (pad) и тремя вспомогательными регистрами (n, d, dat). Функция
перехода состояния, восстановленная из прошивки и верифицированная
побитово против устройства, выглядит так:

  uint32_t yasmarang_next(yasmarang_t *y) {
      y->pad += y->dat + y->d * y->n;
      y->pad = (y->pad << 3) + (y->pad >> 29);   // ротация влево на 3
      y->n   = y->pad | 2;
      y->d  ^= (y->pad << 31) + (y->pad >> 1);
      y->dat ^= (y->pad & 0xFF) ^ ((y->d >> 8) & 0xFF) ^ 1;
      return y->pad ^ (y->d << 5) ^ (y->pad >> 18) ^ (y->dat << 1);
  }

Это качественный statistical PRNG (проходит diehard-подобные тесты при
случайном seed), но он полностью детерминирован своим начальным состоянием.
Криптографической стойкости у него нет и быть не может: зная (pad, n, d,
dat), можно воспроизвести весь будущий поток.

Прошивка Coldcard формирует 32 байта энтропии seed НЕ из одного, а из ДВУХ
инстансов Yasmarang, XOR-ящихся побайтно (8 итераций по 4 байта):

  yasmarang_t chip = { uid ^ systick, RTC->TR, RTC->SSR, 0 };  // "chip path"
  yasmarang_t ngu  = { [REDACTED internal constants] };  // "ngu path"

  for (i = 0; i < 8; i++) {
      uint32_t mixed = yasmarang_next(&chip) ^ yasmarang_next(&ngu);
      // 4 байта mixed -> out[4*i .. 4*i+3]
  }
  // затем: seed32 = SHA256d(out)  ->  BIP-39 мнемоника

Замысел конструкции — смешать "аппаратный" источник (chip path, где pad
берётся из UNIQUE_ID XOR SysTick) с "программным" ngu path. Но из-за
MICROPY_HW_ENABLE_RNG=0 chip path НЕ обращается к аппаратному TRNG (RNG->DR),
а сам является программным Yasmarang. То есть оба потока — детерминированные
PRNG, и XOR двух предсказуемых потоков остаётся предсказуемым.

2.2.2 Коллапс энтропии: почему остаётся ~19-20 бит
--------------------------------------------------------------------------------

Разберём фактические начальные состояния обоих инстансов на реальном Mk3:

  ngu path = { [REDACTED internal constants] }
    ВСЕ четыре поля — жёстко зашитые константы. Следовательно, поток
    yasmarang_next(&ngu) ИДЕНТИЧЕН на каждом устройстве и в каждом запуске.
    Это не источник энтропии, а фиксированная известная маска XOR.

  chip path = { uid ^ systick, RTC->TR, RTC->SSR, 0 }
    На Mk3 макрос MICROPY_HW_ENABLE_RTC=0, поэтому регистры RTC не
    инициализированы: RTC->TR = 0 и RTC->SSR = 0. Значит:
      n   = 0
      d   = 0
      dat = 0
      pad = uid ^ systick   <-- ЕДИНСТВЕННАЯ переменная величина

Таким образом вся энтропия seed сводится к 32-битному значению
pad = UNIQUE_ID_word0 ^ SysTick->VAL. Это принципиально: не 256 бит, не
даже 32 независимых бита, а единственное 32-битное число, чьё эффективное
разнообразие дополнительно ограничено свойствами обоих слагаемых XOR
(разбирается в 2.2.3). Именно поэтому brute-force сводится к перебору
одного параметра PAD (плюс параметра SKIP — числа "прокруток" PRNG до
момента фиксации seed, см. 3.7).

2.2.3 Модель UID и бюджет энтропии STM32L496
--------------------------------------------------------------------------------

MCU Coldcard Mk3 — STM32L496RGT6. 96-битный UNIQUE_ID располагается по
адресу 0x1FFF7590. Для формирования pad используется word0:

  word0 = X[15:0] | Y[31:16]   (координаты кристалла на пластине: X, Y)

Эмпирический анализ 11 реальных STM32 UID (из открытых источников: форумы
ST, GitHub, techoverflow) показал устойчивую структуру:

  #   Chip     word0        X    Y     Wafer  Lot
  --  -------  -----------  ---  ----  -----  --------
   1  L476     0x004A0029   41    74     17   P3XK71
   2  F405     0x0025001E   30    37     12   Q319784
   3  F2       0x006C0028   40   108     20   Q819670
   4  L4/G     0x005D004D   77    93      4   P67A00
   5  L4/G     0x00520033   51    82     14   PBTQ99
   6  F042     0x000C0020   32    12      5   042ACC

Наблюдения (N=11):
  - X in [30, 77], Y in [12, 108] — координаты укладываются в один байт;
  - все word0 имеют вид 0x00YY00XX — старшие байты каждой координаты = 0;
  - эффективная энтропия word0 ~= 14 бит (X ~7 бит + Y ~7 бит);
  - UID НЕ секретен: утекает через USB serial и machine.unique_id().

Итоговый бюджет энтропии Mk3 seed:

  Компонент                        Вклад
  -------------------------------  ------------------------------------
  UNIQUE_ID word0 (X,Y)            ~14 бит (кластеризован по партиям)
  SysTick->VAL на момент генерации несколько бит (узкое временное окно)
  RTC->TR, RTC->SSR                0 бит (RTC отключён)
  ngu path (константа)             0 бит
  -------------------------------  ------------------------------------
  ЭФФЕКТИВНО                       ~19-20 бит

Эмпирически восстановленный диапазон PAD (0x000F02C9 - 0x004BF595) и
кластеризация по производственным партиям подтверждают эту оценку:
пространство реальных значений pad составляет ~4.5 млн, а не 4.3 млрд,
что и делает исчерпывающий перебор тривиальным.

2.5 Оценка Mk4: УЯЗВИМ (тот же баг, исправлено только в 5.6.0)
--------------------------------------------------------------------------------

ВАЖНО (пересмотр v4): настоящий раздел переработан по результатам прямого
аудита исходников прошивки Mk4 (github.com/Coldcard/firmware + submodule
libngu-компонента), проведённого в отдельной Mk4-фазе (5 раундов).
Ранняя оценка "~56 бит, infeasible" ОПРОВЕРГНУТА исходным кодом.

2.5.1 Mk4 разделял ту же уязвимость
Прошивка Mk4 5.0.0 (март 2022) — 5.5.1 (июль 2026) использовала ТОТ ЖЕ
Yasmarang PRNG, что и Mk3. Официальный ChangeLog Coinkite (Security Advisory,
июль 2026), дословно:
  "Versions from 2021 to July 2026 had a bug which produced poor entropy."
  "Master seeds can only be trusted from releases after:
     5.6.0 (Mk4, MK5), 4.2.0 (Mk3), 1.5.0Q (Q1), 6.6.0 (Edge)."

2.5.2 SE reseed усекался до 32 бит (НЕ спасал)
Замысел Mk4 — reseed Yasmarang от двух Secure Element. Но старый
shared/mk4.py::rng_seeding() (до фикса ac1644cd, 2026-08-14) содержал:

  a = callgate.read_rng(1)          # SE1
  b = callgate.read_rng(2)          # SE2
  n = ngu.hash.sha256d(a+b)
  n, = ustruct.unpack('I', n[0:4])  # <-- УСЕЧЕНИЕ 256 -> 32 бита
  ngu.random.reseed(n)

То есть 256-битный SE-дайджест усекался до 32 бит перед reseed. Более того,
сама генерация seed (shared/seed.py::generate_seed до фикса 493b77c3) НЕ
примешивала SE вообще:

  seed = ngu.random.bytes(32)       # только Yasmarang
  return ngu.hash.sha256d(seed)

Реальный потолок уязвимого Mk4 = 2^32 (усечение reseed), а НЕ 2^56.
Этот пересмотр подтверждён после предъявления исходного кода.

2.5.3 Таймлайн модели и фиксы (git-история прошивки)
  generate_seed = sha256s(random.bytes(32))    старт 2022 (Mk4 5.0.0)
    -> sha256d(random.bytes(32))  commit 024655be  2024-01-10 (шип ~5.3.x)
  фикс: SE-mixing в seed          commit 493b77c3  2026-08-14 (5.6.0)
  фикс: full-256 boot reseed      commit ac1644cd  2026-08-14 (5.6.0)

Криптографический компонент (libngu) подключён к прошивке как submodule;
его разработка/мерж security-critical кода без независимого review — ключевой
процессный фактор (см. Раздел 7).

2.5.4 Эмпирический результат Mk4-сканов
Несмотря на подтверждённую уязвимость, GPU-сканы прямого sha256d-флоу Mk4
(pad 0..2^25, skip 0-32, индексы 0-4; ~1.07 млрд кандидатов) дали 0 хитов.
Валидация пайплайна пройдена (мини-ceremony модель переоткрыла известную
Mk3-жертву PAD=0x0012563E). Интерпретация нулевого результата:
  - жертвы Mk4 использовали mini-ceremony (тот же путь, что Mk3) и по адресам
    НЕОТЛИЧИМЫ от наших 2,052 seed -> часть из 2,052 может фактически быть Mk4;
  - прямой sha256d-флоу (эпоха 2024+) либо не дал уязвимых seed в текущем
    victim list, либо эти жертвы применяли dice/passphrase (невосстановимо);
  - непокрытые 889 bc1q-жертвы (88% с первым UTXO в 2024+, timeline-forensics)
    с высокой вероятностью относятся к этой эпохе и НЕ поддаются brute-force
    (кубики / passphrase / прошивка 5.6.0+).

ВЕРДИКТ (пересмотрен): Mk4 УЯЗВИМ на всех версиях до 5.6.0. "Спасало" его не
корректная конфигурация RNG, а лишь то, что усечённый reseed давал 2^32, и
массовая эксплуатация сфокусировалась на более лёгком Mk3. Практическое
восстановление Mk4-специфичных seed нашим методом дало 0 дополнительных хитов
(жертвы неотличимы от Mk3-набора либо использовали митигации) — но публичное
заявление "Mk4 не уязвим" фактически НЕВЕРНО.

2.6 Пошаговая реконструкция эксплуатации (exploit walkthrough)
--------------------------------------------------------------------------------

Полный путь от загрузки устройства до предсказуемого seed на уязвимой
прошивке Mk3 выглядит так:

  Шаг 1. При старте / генерации seed вызывается generate_seed()
         (firmware_seed.py:605), которая запрашивает 32 байта энтропии:
         seed = ngu.random.bytes(32).

  Шаг 2. ngu.random.bytes() -> random_bytes() -> my_random_bytes(dest, 32)
         (random.c:68). Внутри формируется поток байт как
         CHIP_TRNG_32() XOR my_yasmarang().

  Шаг 3. CHIP_TRNG_32() = rng_get(). Из-за MICROPY_HW_ENABLE_RNG=0 функция
         rng_get() скомпонована на pyb_rng_yasmarang(), а НЕ на RNG->DR.
         Таким образом ОБЕ половины XOR являются программным Yasmarang с
         предсказуемым состоянием (pad = UNIQUE_ID ^ SysTick, n/d/dat
         фиксированы). XOR двух предсказуемых потоков остаётся предсказуемым.

  Шаг 4. Полученные 32 байта пропускаются через sha256d и кодируются в
         24-словную BIP-39 мнемонику. Вся энтропия seed определяется
         единственным значением pad (~19-20 эффективных бит).

  Шаг 5. На пути от загрузки к моменту фиксации seed PRNG успевает
         "прокрутиться" некоторое число раз (навигация по UI, PIN-ceremony,
         mini-ceremony). Это число — параметр SKIP — сдвигает состояние
         PRNG. Атакующий перебирает пары (PAD, SKIP), симулируя ту же
         последовательность вызовов, что и прошивка.

  Шаг 6. Для каждого кандидата вычисляется мнемоника -> BIP84 master key ->
         адреса recv[0..4]. Если хотя бы один адрес присутствует в bloom
         (когда-либо использован в сети Bitcoin), кандидат помечается как
         вероятный хит и подтверждается полной деривацией.

Именно эта детерминированность (фиксированные внутренние константы и узкое
распределение pad) превращает 256-битную по замыслу генерацию в перебор
~1.56 млрд вариантов — задачу минут на одной GPU. Атакующему не нужен
физический доступ к устройству жертвы: достаточно знать модель PRNG и
диапазон pad/SKIP, после чего он генерирует все возможные seed'ы и
сопоставляет их адреса с блокчейном.

3.1 GPU Brute-Force (mc24w — Mini Ceremony 24-word)
--------------------------------------------------------------------------------

GPU-ускоренный перебор состояния PRNG Yasmarang:

  - PAD диапазон:  0x000000 — 0x4FFFFF (~5.2 млн кандидатов)
  - SKIP диапазон: 3 — 300 (шаги навигации в ходе seed-ceremony; позже
                расширен до ~1024)
  - Для каждой пары (PAD, SKIP): симуляция ceremony -> вывод BIP-39
    мнемоники -> вычисление BIP84 receive-адресов (индексы 0-4) ->
    проверка через bloom filter.

  Оборудование: NVIDIA GPU с кастомным CUDA BIP32-ядром
  Скорость:     ~134,823 кандидатов/с
  Всего:        ~1.56 млрд кандидатов (5.2M PAD x ~298 SKIP)

Модель ceremony: mc24w (mini-ceremony) и pc24w (pin-ceremony) — два способа
запуска генерации seed на устройстве, различающиеся числом навигационных
шагов (SKIP), потребляющих значения PRNG до момента фиксации энтропии seed.

3.2 Bloom Filter (Loyce, 1.57 млрд адресов)
--------------------------------------------------------------------------------

Источник: loyce.club all_Bitcoin_addresses_ever_used_sorted.txt + daily
updates (19-22 августа 2026). Апдейт 22 авг домержён отдельно (+1,256,589
уникальных новых адресов после дедупликации против основного файла); версии
bloom v4 пересобираются на обновлённом наборе.

  - 1,571,613,883 адресов (ВСЕ типы, включая дренированные)
  - FP rate: 1e-7
  - Размер:  8.39 GB, 24 хэш-функции (MurmurHash3_x64_128, double hashing)
  - Сборка:  C# (bloom_builder.cs), 38.6 мин, 678K addr/s
  - Верификация: 6541/6541 victim-адресов (100%)

КРИТИЧЕСКОЕ УЛУЧШЕНИЕ: исходный bloom filter содержал ТОЛЬКО адреса с
балансом > 0, пропуская ВСЕ дренированные адреса жертв. Loyce bloom
содержит все адреса, когда-либо использованные в сети Bitcoin, что
раскрыло ~70% ранее скрытых жертв. Именно этот переход дал скачок с 600
до 2,052 seeds.

Дополнительно построен H160 bloom для GPU-резидентной проверки:
  - 421,087,720 bc1q-адресов (h160 хэши)
  - 1.797 GB, k=13, FP=3.22e-7
  - Верификация: 5283/5283 victim bc1q h160s (100%)

3.3 Многоиндексное сканирование (Blind Spot Fix)
--------------------------------------------------------------------------------

Фаза 1: только индекс 0 (исходный подход)     -> 600 seeds (master v7)
Фаза 2: индексы 0-4 (исправление слепого пятна)
  Слепое пятно: seed'ы, где recv[0] отсутствовал в bloom (например,
  адрес был sweep'нут до попадания в снапшот bloom). Исправление —
  проверка индексов 0-4 в prefilter (~0.2% доп. накладных расходов).
  -> 1,399 новых seeds (idx 0) + 52 новых seeds (idx 1)
Фаза 3: индексы 2-4                            -> 0 новых seeds
  (все 322 хита уже присутствовали в результатах idx 0+1 -> покрытие
  idx 0+1 составляет ~100%)

3.4 Deep Derivation (глубина 10,000)
--------------------------------------------------------------------------------

Для всех 2,052 восстановленных seed:

  - 10 путей BIP84 x 10,000 глубина (recv[0-9999] + chng[0-9999] для
    аккаунтов 0-4)
  - Всего деривации: ~205,200,000
  - Оборудование: GPU BIP32-ядро с оптимизацией shared-memory + H160 bloom
  - Длительность: ~1.8 часа

  Результат: 35,189 попаданий по адресам
    - 4,399 VICTIM-совпадений на этапе deep-скана (классификация hit'ов;
      итоговое дедуплицированное пересечение с victim list = 4,407, см. Прил.D)
    - 30,789 BLOOM (в Loyce bloom, но не в списке жертв)
    - 19,185 адресов ранее не были известны
    - доминирующий путь: BIP84 account 0 (99.2% всех попаданий)

Всего протестировано 48 путей деривации (BIP84/44/49/86/48/bare/BIP45);
попадания дал практически только BIP84 account 0 — non-BIP84 пути дали
0.8% адресов. Это позволило оптимизировать deep derivation до BIP84-only
(экономия ~13.5 часов compute).

      internal — обе стороны принадлежат нашему набору адресов
                 (change-cycling внутри одного seed);
      external — депозит извне (реальное поступление средств);
      mixed    — смешанные входы (учтены как external).
  - Net Stolen = external + mixed депозиты.
  - Gap filler добрал 16,700 непокрытых адресов (342.5 мин, 0 ошибок);
    JSON-результат записан полностью до краша печати (cp1251 bug, на
    данные не влияет).

3.7 Модель ceremony и устройство GPU-ядра
--------------------------------------------------------------------------------

Параметр SKIP отражает число обращений к PRNG между reseed и моментом
фиксации энтропии seed. Устройство предлагает несколько путей генерации,
различающихся этим числом:

  mc24w (mini-ceremony 24-word): короткий путь, диапазон SKIP 3-300 (позже
    расширен до ~1024). Основной продуктивный вектор — дал практически все 2,052 seed.
  pc24w (pin-ceremony 24-word): путь с вводом PIN, параметризуется парой
    (PIN-длина, NAV-шаги). Полностью просканирован (PIN 1-20, NAV 1-75) —
    новых seed не дал: все pc24w-хиты сводятся к уже известным PAD из mc24w.

Эмпирически распределение SKIP концентрируется в узком диапазоне 6-295 (с
единственным выбросом при 502) с пиком на SKIP=12 (108 seeds). Теоретический
максимум оценивается в ~500 (соответствует ~19 отказам в ходе ceremony) —
эмпирически подтверждён одним seed, восстановленным при SKIP=502. Скан SKIP
301-400 на 524M кандидатов дал 0 хитов; последующий расширенный скан SKIP
401-1024 дал ровно один дополнительный seed (при SKIP=502), показав, что хвост
за основной полосой крайне разрежен, но не строго пуст. Значения SKIP выше ~1024
не сканировались; ожидаемый вклад пренебрежимо мал.

CUDA BIP32-ядро — ключевой элемент производительности:

  - window-8 precomputation для скалярного умножения на кривой secp256k1;
  - shared-memory резидентный H160 bloom (1.797 GB) для мгновенной
    проверки hash160 адресов прямо на GPU без обращения к хосту;
  - многоиндексный prefilter (индексы 0-4) для устранения слепого пятна
    (случаи, когда recv[0] отсутствует в снапшоте bloom);
  - для deep derivation — генерация до глубины 10,000 по recv и change
    ветвям аккаунтов 0-4.

Производительность: ~134,823 кандидата/с на этапе brute-force seed и
~205M деривации за ~1.8 часа на этапе deep 10K. Для сравнения, чисто CPU-
реализация deep 10K заняла бы ~39 часов; перенос BIP32 на GPU дал
ускорение примерно в 100x. Paper wallet вектор (без BIP-39/PBKDF2) на GPU
достигает ~50M ключей/с — в ~370x быстрее seed-перебора, но 0 хитов в
списке жертв указывают, что paper wallets либо не использовались жертвами,
либо отсутствуют в текущем victim list.


3.8 Цепочка деривации адресов: BIP-39 -> BIP-32 -> BIP-84
--------------------------------------------------------------------------------

От восстановленного 32-байтного значения энтропии до конкретного
bc1q-адреса ведёт стандартная детерминированная цепочка. Точное её
воспроизведение критично: любая ошибка в пути деривации даёт другие
адреса и ложное "0 хитов".

  Шаг 1 (BIP-39). Энтропия -> мнемоника.
    entropy32 = SHA256d(raw_yasmarang_output)
    24-словная мнемоника = кодирование (entropy || checksum) по словарю
    BIP-39 (2048 слов, 11 бит на слово). Для 256 бит энтропии + 8 бит
    контрольной суммы = 264 бита = 24 слова.

  Шаг 2 (BIP-39 seed). Мнемоника -> 512-битный seed.
    seed512 = PBKDF2-HMAC-SHA512(mnemonic, "mnemonic" + passphrase,
                                  2048 итераций)
    Именно 2048 итераций PBKDF2 — главный тормоз brute-force seed'ов
    (~134K кандидатов/с). Paper wallets минуют этот шаг (нет BIP-39),
    отсюда их перебор в ~370x быстрее.

  Шаг 3 (BIP-32). seed512 -> master key.
    (master_priv, master_chaincode) = HMAC-SHA512("Bitcoin seed", seed512)
    Далее иерархическая деривация по пути с закалёнными (hardened) и
    обычными индексами через повторный HMAC-SHA512.

  Шаг 4 (BIP-84 путь). Для Native SegWit (bc1q):
    m / 84' / 0' / account' / change / index
      84'   = purpose (BIP-84, P2WPKH)
      0'    = coin_type (Bitcoin mainnet)
      account' = номер аккаунта (0 у 99%+ жертв)
      change   = 0 (receive) или 1 (change)
      index    = 0..N (у нас 0..9999 в deep 10K)

  Шаг 5 (адрес). pubkey -> адрес.
    pubkey (33 байта, compressed) -> HASH160 = RIPEMD160(SHA256(pubkey))
    -> bech32-кодирование с witness version 0 -> bc1q...

Именно на уровне HASH160 работает GPU-резидентный H160 bloom: ядро
вычисляет 20-байтный hash160 прямо на устройстве и проверяет его в bloom
без обращения к хосту. Проверялись 48 путей (BIP84/44/49/86/48/bare/BIP45),
но фактически все попадания дал BIP84 account 0 (99.2%), что подтверждает
профиль жертв как пользователей Native SegWit по умолчанию.

3.9 Математика bloom filter
--------------------------------------------------------------------------------

Bloom filter — вероятностная структура, дающая "точно нет" или "возможно
да". Для форензики выбор параметров критичен: слишком высокий FP порождает
ложные хиты (каждый требует дорогой полной деривации и проверки on-chain),
слишком большой фильтр не помещается в память GPU/хоста.

Параметры Loyce bloom:
  n (элементов)   = 1,571,613,883 адресов
  p (целевой FP)  = 1e-7
  m (бит массива) = ceil(-n * ln(p) / (ln 2)^2) ~= 6.75e10 бит ~= 8.39 GB
  k (хэш-функций) = round((m/n) * ln 2) = 24

Двойное хэширование (double hashing) вместо 24 независимых хэшей:
  h1, h2 = две 64-битные половины MurmurHash3_x64_128(addr)
  для i в [0, k): bit_index = (h1 + i * h2) mod m
  КРИТИЧНО: (h1 + i*h2) вычисляется в uint64 с переполнением по маске
  & 0xFFFFFFFFFFFFFFFF, иначе индексы расходятся с построением фильтра и
  дают ложные промахи. Эта деталь была источником ранней ошибки и
  зафиксирована как обязательное правило реализации.

Почему это раскрыло в 3.4x больше жертв: исходный bloom содержал только
адреса с балансом > 0 (снапшот UTXO), поэтому ВСЕ дренированные адреса
(баланс = 0, но с историей) были невидимы. Loyce bloom содержит все
адреса, когда-либо участвовавшие в транзакциях, — именно они и составляют
массу жертв, чьи средства уже украдены.

H160 bloom (GPU-резидентный) построен только на 421M bc1q-адресах и хранит
20-байтные hash160 напрямую, что позволяет проверять кандидата на GPU без
кодирования в bech32-строку — экономия на каждом из ~205M деривации
deep-скана.

3.10 Алгоритм классификации TX Graph (Net Stolen)
--------------------------------------------------------------------------------

Gross total_received систематически завышает ущерб: когда жертва тратит
средства, сдача возвращается на change-адрес того же seed'а — и повторно
засчитывается как "поступление". Чтобы получить чистый украденный объём,
каждая из 46,131 транзакции классифицируется по составу входов и выходов
относительно множества V всех 35,189 адресов жертв.

  Определим для транзакции T:
    inputs_from_V  = входы, принадлежащие адресам из V
    outputs_to_V   = выходы, идущие на адреса из V
    external_in    = входы, НЕ принадлежащие V

  Классификация:
    INTERNAL  — все входы из V И все выходы в V (сдача/перемещение внутри
                кошелька жертвы). Объём НЕ считается украденным.
    EXTERNAL  — входы извне V (реальное поступление на адрес жертвы).
                Объём outputs_to_V засчитывается как поступивший ущерб.
    MIXED     — входы частично из V, частично извне. Консервативно
                учитывается как external (не занижаем ущерб).

  Net Stolen = сумма external-депозитов + mixed-депозитов.

Результат:
  46,131 TX = 9,159 internal + 36,931 external + 41 mixed
  Gross 10,950.75 BTC
    - internal 5,869.83 BTC (53.6%)  <- НЕ ущерб (change cycling)
    - external 5,076.71 BTC (46.4%)  <- реальные поступления
    - mixed        3.19 BTC          <- учтено как external
  NET STOLEN = 5,079.90 BTC

Граничные случаи и корректность:
  - Транзакции с несколькими выходами в V учитываются пофакторно (только
    та часть, что попала в V).
  - Consolidation-транзакции самого атакующего (сбор с многих адресов
    жертв на его хаб) классифицируются как EXTERNAL со стороны входов V:
    это момент фактической кражи, средства покидают периметр жертвы.
  - Покрытие: 35,189/35,189 адресов (100%), 0 ошибок сбора истории.
  Итоговая цифра 5,079.90 BTC получена из полного графа и не подвержена
  возражению "это internal transfers".


3.11 Конвейер верификации балансов и forensic-сбора
--------------------------------------------------------------------------------

Достижение 100% покрытия по балансам для 35,189 адресов потребовало
многопроходного конвейера, комбинирующего несколько источников данных, так
как ни один единственный источник не давал полного и корректного
результата. Ниже описаны проходы и обнаруженные при этом систематические
ошибки, исправление которых существенно повлияло на итоговые цифры.

Проход 1 — Electrum forensic (SSL). Основной источник: прямое подключение
к серверам Electrum по протоколу SSL с запросом полной истории транзакций
по scripthash каждого адреса. Покрыл 18,071 адрес с полными данными по TX и
балансу. Этот проход также поставляет входы/выходы, необходимые для
последующего TX-graph анализа (Раздел 3.10).

Проход 2 — REST API (blockstream.info, blockchain.info, btcscan.org).
Использовался как быстрый параллельный источник и как fallback там, где
Electrum-сервер отвечал таймаутом. Покрыл 2,459 адресов.

Проход 3 — Electrum total_received (raw TX parsing). Для адресов, где нужен
был именно суммарный lifetime-объём поступлений (а не текущий баланс),
история транзакций разбиралась вручную для подсчёта total_received. Покрыл
10,825 адресов.

Проход 4 — pending sweep. Финальный добор 445 адресов, не покрытых
предыдущими проходами, через комбинацию Electrum + REST fallback.

Проход 5 — Zero-BTC fix. КРИТИЧЕСКИЙ проход. Обнаружилось, что ранние
запросы через часть Electrum-эндпойнтов возвращали баланс 0 для адресов,
которые в действительности имели значительный исторический total_received
(дренированные адреса: текущий баланс 0, но lifetime-поступления больше 0).
Эта систематическая ошибка (условно Electrum zero-BTC bug) занижала
суммарную оценку. Повторный разбор raw-транзакций для 5,849 затронутых
адресов добавил около 6,155 BTC к суммарному Gross. Именно этот фикс
объясняет скачок с ~4,800 BTC (промежуточная оценка R65-R67) до итоговых
10,950 BTC Gross.

Итог по покрытию:
  Electrum forensic (SSL)        18,071 адресов (полные TX + баланс)
  Electrum total_received        10,825 адресов (raw TX parsing)
  Zero-BTC fix (Electrum)         5,849 адресов (+~6,155 BTC)
  REST API (blockstream и др.)    2,459 адресов
  Pending sweep                     445 адресов
  Individual balance files        (частично перекрываются)
  ------------------------------------------------------
  ВСЕГО                          35,189 / 35,189 = 100%

Все 35,189 адресов имеют статус DRAINED (баланс 0, TX больше 0). Активных
балансов — 0. Это означает, что на момент завершения аудита ни на одном из
восстановленных адресов не осталось средств: периметр полностью
обескровлен. Данный факт подтверждает завершённость кражи: на самих
восстановленных адресах спасать уже нечего. Автор не ведёт наблюдения за
этими адресами и не совершает с ними никаких операций — восстановление
seed при нулевых балансах не создало для жертв никакого нового риска.

TX-graph gap filler. Для расчёта Net Stolen требовалась полная история
транзакций (а не только баланс) для всех адресов. 16,700 адресов, не
покрытых forensic-проходом 1, добирались отдельным gap-filler-ом (3
параллельных Electrum-сервера, 342.5 минуты, 0 ошибок). Технический
нюанс: процесс печати итоговой сводки аварийно завершался из-за
несовместимости кодировки консоли (cp1251 против Unicode box-drawing
символов), ОДНАКО JSON-результат записывался на диск ПОЛНОСТЬЮ до момента
краша печати. Проверка целостности JSON подтвердила корректность всех
46,131 классифицированной транзакции. Данный краш — косметический баг
вывода, на данные и итоговые цифры не влияющий.

4.4 Что означает internal ratio 53.6%
--------------------------------------------------------------------------------

53.6% всего объёма (5,869.83 BTC) — это внутренние переводы между адресами
одних и тех же жертв (change-outputs при обычных тратах: пользователь
отправлял средства сам себе на автоматически сгенерированный change-адрес
того же seed'а). Эти суммы НЕ являются украденными — это тот же биткоин,
циркулирующий внутри кошелька жертвы, многократно засчитываемый в Gross.

Оставшиеся 46.4% (5,076.71 BTC external + 3.19 BTC mixed = 5,079.90 BTC) —
это реальные внешние поступления на скомпрометированные адреса, которые в
конечном счёте были похищены. Это математически железобетонная цифра
чистого ущерба, рассчитанная из полного графа транзакций (100% покрытие) и
не подверженная возражению "это internal transfers".

Определения для использования в коммуникации:
  Gross Compromised Volume (10,950 BTC / $861M) — общий объём, прошедший
    через скомпрометированные ключи; показывает МАСШТАБ проникновения
    уязвимости.
  Net Stolen (5,080 BTC / $399M) — ФАКТИЧЕСКИЙ ущерб; неоспоримая метрика.

Прогноз (internal ratio вырастет до 60-65% при 100% coverage) не
подтвердился: фактический internal составил 53.6%, то есть чистый ущерб
оказался ВЫШЕ прогноза.

4.5 Cross-chain $0: подтверждение Bitcoin-only профиля жертв
--------------------------------------------------------------------------------

Нулевой результат на всех 11 цепочках (123,060 адресов) доказывает: жертвы
Coldcard Mk3 не импортировали свои seed'ы в мультивалютные кошельки
(MetaMask, Trust Wallet и т.п.) и использовали устройство строго по
назначению — как Bitcoin-only холодное хранилище. Это косвенно
подтверждает, что мультиадресный (BIP44/49/86) rescan имеет низкий ROI:
BTC-only пользователи не задействовали legacy/P2SH/taproot пути в объёме,
оправдывающем дополнительное сканирование. Оценка R66 в "$500M+" с учётом
кросс-чейн активов — ОТМЕНЕНА; итоговый ущерб исключительно в BTC.


4.6 Реконсиляция энтропии: 2^40.69 (BlockSec) vs 2^19-20 (наш аудит)
--------------------------------------------------------------------------------

BlockSec оценил потолок Mk3 как 2^40.69. Это не ошибка, а иная точка
измерения. Расхождение объясняется тем, ЧТО именно моделируется:

  BlockSec (2^40.69):
    Моделирует пространство состояний PRNG Yasmarang — комбинаторику всех
    достижимых внутренних состояний при варьировании входов. Это верхняя
    теоретическая граница, если бы 32-битный pad плюс сопутствующие
    регистры были независимо-случайными.

  Наш аудит (2^19-20):
    Измеряет ВХОДНУЮ энтропию, реально доступную устройству. Как показано
    в 2.2.2-2.2.3, chip path на Mk3 имеет n=d=dat=0 (RTC отключён), ngu
    path — константа, и единственная переменная pad = UID_word0 ^ SysTick.
    word0 несёт ~14 бит (координаты кристалла X,Y в один байт каждая),
    SysTick добавляет несколько бит в узком временном окне.

Ключ к расхождению: пространство состояний PRNG может быть большим, но
если на вход подаётся всего ~19-20 бит энтропии, то достижимо лишь ~2^20
различных выходных потоков. Остальные "состояния" из оценки 2^40.69
недостижимы, потому что соответствующие входы никогда не возникают на
реальном железе. Эмпирическое подтверждение — наблюдаемый диапазон PAD
(0x000F02C9 - 0x004BF595, ~4.5M значений) и успешное восстановление 2,052
seeds перебором ~1.56 млрд кандидатов (PAD x SKIP).

Практический вывод: официальная формулировка Coinkite ("~72 бита энтропии
вместо 128") занижает тяжесть на порядки. Реальная эффективная энтропия
~19-20 бит делает атаку не "теоретически ослабленной", а тривиально
исполнимой на одной GPU за минуты.

4.7 Анализ недостижимых seed'ов (feasibility ceiling)
--------------------------------------------------------------------------------

Из ~35,189 адресов victim-периметра список 6,541 "официальных" жертв
покрывает лишь ~18.6%. Разрыв между тем, что можно восстановить нашим
методом, и полным множеством пострадавших объясняется категориями,
принципиально не поддающимися brute-force:

  Категория                    Оценка seed'ов   Причина недостижимости
  ---------------------------  ---------------   ---------------------------
  Mk4/Mk5/Q (до 5.6.0)         (см. 2.5)         УЯЗВИМЫ (2^32), но seed
                                                 неотличимы от Mk3 либо
                                                 dice/passphrase -> 0 доп.хитов
  Dice-roll seeds              ~200-500          физическая энтропия, не PRNG
  BIP-39 passphrase users      ~200-500          внешняя энтропия в KDF
  SKIP > 300                   ~0 (оч. разрежено) 301-400: 0; 401-1024: 1 (SKIP 502)
  Нестандартная деривация      частично покрыто  multisig m/48', legacy paths
  ---------------------------  ---------------   ---------------------------
  Итого недостижимо            ~700-1500 seeds

При этом для восстановимой популяции (Mk3 PRNG с историей транзакций)
покрытие составляет ~99%+ (2,052 из потолка ~2,070). Оценка потолка
основана на насыщении: индексы 2-4 после idx 0+1 дали 0 новых seeds, а
SKIP 301-400 дал 0 хитов (расширенный скан 401-1024 добавил лишь один seed при
SKIP=502) — сигналы того, что продуктивное пространство поиска почти исчерпано.

4.7.1 Gap по не-bc1q адресам (лимитация метода)
--------------------------------------------------------------------------------

Отдельная лимитация касается типов адресов. Наш prefilter проверял в bloom
преимущественно bc1q (BIP84), поэтому жертвы, пополнявшие ТОЛЬКО legacy (1...),
P2SH (3...) или taproot (bc1p), не детектировались на этапе брута. В victim
list 6,541:

  Тип             Восстановлено   Всего в victim list   Покрытие
  --------------  --------------   -------------------   --------
  bc1q (BIP84)    4,394            5,283                 83.2%
  legacy (BIP44)  11               777                   1.4%
  P2SH (BIP49)    2                295                   0.7%
  taproot (BIP86) 0                186                   0.0%

Проверка (деривация всех 2,052 seed по 48 путям x глубина 10,000): 0 из 1,245
не-bc1q victim-адресов выводятся из наших seed. Гипотеза: ~1,245 не-bc1q жертв =
ОТДЕЛЬНЫЕ ненайденные seed (их владельцы не пополняли bc1q, поэтому bc1q-bloom
их пропустил). Для проверки собран all-types h160-bloom (1,421,683,820 хэшей:
bc1q+legacy+P2SH; все 1,072 legacy/P2SH victim-адреса в нём) и выполнен
брут-скан моделью mini-ceremony (pad 0..0x600000, shuffle 3-300, multi-address
prefilter BIP84+BIP49+BIP44), покрывающий весь эмпирический диапазон PAD.

РЕЗУЛЬТАТ Gap B (ОКОНЧАТЕЛЬНЫЙ): 2,051 хитов, из которых 2,042 = уже известные
Mk3-seed (переоткрытие), 9 "новых". Deep-деривация этих 9 (48 путей x 10,000
глубина, независимый h160-bloom) дала 0 victim и 0 bloom совпадений, а их
match-адреса ОТСУТСТВУЮТ в victim-листе -> 9 "новых" = BLOOM FALSE POSITIVES
(loyce string-bloom, FP ~1e-7). Итог: Gap B = 0 подтверждённых новых жертв.

ВЫВОД: прогноз (+300-400 seed) НЕ подтвердился. Не-bc1q victim-адреса
НЕ восстанавливаются новыми mini-ceremony seed — следовательно они принадлежат
либо тем же 2,052 seed (через нестандартные пути), либо seed с BIP-39
passphrase / кубиковой (dice) энтропией, которые математически невосстановимы.
Для полноты просканирован и верхний диапазон pad 0x600000..0x1000000
(3,124,756,480 кандидатов, той же моделью): 0 хитов. Таким образом весь
диапазон pad 0..2^24 покрыт с нулевым приростом настоящих жертв.
Восстановление популяции, уязвимой из-за бага Yasmarang, практически завершено
на 2,052 seed (~99% от оценки ~2,070). Extended-shuffle скан (SKIP до ~1024)
восстановил ещё один seed при SKIP=502 — эмпирически подтвердив теоретический
максимум ~500 — и никаких других; хвост за основной полосой SKIP тонкий, но не
строго пуст, а значения SKIP выше ~1024 не сканировались (ожидаемый вклад
пренебрежимо мал). Taproot (32-байт x-only, BIP341) остаётся
единственным непроверенным типом; ожидаемый вклад пренебрежимо мал (186 из
6,541 victim = 2.8%, при нулевом результате по остальным типам).

4.8 Кросс-чейн деривация: техническая детализация нулевого результата
--------------------------------------------------------------------------------

Нулевой кросс-чейн результат — это не отсутствие проверки, а результат
исчерпывающей деривации по алгоритмам каждой из целевых цепочек. Один и тот
же 512-битный BIP-39 seed порождает валидные адреса на любом блокчейне,
использующем стандартную HD-деривацию; если бы жертвы импортировали seed в
мультивалютные кошельки, средства на этих цепочках были бы столь же
уязвимы и, вероятно, уже украдены. Проверка каждой цепочки требует точного
воспроизведения её схемы деривации:

  EVM-семейство (ETH, BSC, Polygon, Avalanche, Arbitrum, Optimism, Base):
    Единый путь m/44'/60'/0'/0/N (secp256k1). Публичный ключ (uncompressed,
    без префикса) -> Keccak256 -> младшие 20 байт -> адрес 0x... Один и тот
    же приватный ключ действителен на ВСЕХ EVM-цепочках, поэтому одна
    деривация покрывает всё семейство; проверка токенов (ERC-20: USDT,
    USDC) выполняется помимо нативного баланса.

  UTXO-семейство secp256k1:
    LTC   m/44'/2'/0'/0/N   -> P2PKH/bech32 (L.../ltc1...)
    BCH   m/44'/145'/0'/0/N -> CashAddr (q.../legacy 1...)
    DOGE  m/44'/3'/0'/0/N   -> P2PKH (D...)
    DASH/ZEC (transparent)  -> через Blockchair API
    Отличие от Bitcoin — только version bytes и кодирование; сама
    кривая и деривация идентичны.

  TRX (Tron): m/44'/195'/0'/0/N, secp256k1 + Keccak256 + префикс 0x41 ->
    base58check (T...). Проверка нативного TRX и TRC-20 (USDT).

  SOL (Solana): m/44'/501'/N', кривая ED25519 (НЕ secp256k1). Требует
    отдельной ED25519-HD деривации из того же 512-битного seed; адрес =
    base58 публичного ключа.

  XRP, ATOM: проверены через соответствующие RPC/LCD.
  XMR (Monero): исключён — нестандартная EdDSA-деривация, не выводимая из
    BIP-39 seed без Monero-специфичного инструментария.

Итог: 123,060 адресов на 11 цепочках, 0 хитов, $0. Это положительно
доказывает Bitcoin-only профиль жертв Coldcard (устройство использовалось
строго как холодное хранилище BTC) и снимает гипотезу R66 о "$500M+ с
учётом кросс-чейн активов". Ущерб исключительно в BTC.

5.5 Статистическая модель поведения бота
--------------------------------------------------------------------------------

Профиль 202 волн и распределение задержки drain позволяют реконструировать
операционную модель раннего оператора (Фаза 1) как автоматизированного
бота, а не серии ручных краж:

  1. НЕПРЕРЫВНЫЙ МОНИТОРИНГ. Медианная задержка от пополнения адреса до его
     дренирования — 653 дня, при этом 47.1% адресов дренированы спустя
     2+ года. Ручной оператор не отслеживал бы тысячи адресов годами;
     это поведение сканера, непрерывно сверяющего blockchain с заранее
     сгенерированным множеством скомпрометированных seed'ов.

  2. ПОРОГ БАЛАНСА. Разброс сумм на волну (от 0.01 до 78 BTC) и то, что
     drain часто следует вскоре за крупным поступлением, согласуется с
     правилом "выводить при поступлении средств выше порога", а мелкие
     остатки подбирать оптовыми consolidation-волнами.

  3. РЕГУЛЯРНОСТЬ, НЕ СЛУЧАЙНОСТЬ. Волны распределены по всему периоду
     2021-2026 с пиком в 2022 (соответствует пику продаж уязвимых Mk3).
     Помесячная кривая новых дренированных адресов является прокси окна
     уязвимости: рост в 2021-2022, спад после ~2023 (выход патча 4.2.0).

  4. КОНСОЛИДАЦИЯ С ЗАДЕРЖКОЙ. Ранний бот держал 51.07 BTC два года и
     консолидировал в хаб лишь за 3 месяца до публичных волн (2026-04-27).
     Это поведение "накопителя", уверенного в незаметности уязвимости, а
     не спешащего обналичить оппортуниста.

  5. ФАЗОВЫЙ ПЕРЕХОД НА DISCLOSURE. 201 волна Фазы 1 (медленное
     обескровливание) сменяется единственной гигантской Волной 202
     (6,354 адреса, 1,667 BTC за ~3 дня) сразу после публичного раскрытия
     30 июля 2026. Резкое изменение паттерна (масса адресов, распыление по
     сотням новых адресов вместо единого хаба, "sweep rate 45x baseline")
     указывает на выход множества копикэтов (15-25+ по оценкам TRM/Galaxy)
     в режиме "золотой лихорадки" за общий keyspace.

Практический вывод для трассировки: Фаза 1 атрибутируется 1-2 субъектам с
устойчивой инфраструктурой (бот -> хаб bc1qc779m8...7ueyn), тогда как
Фаза 2 — множеству независимых операторов; их следует разделять при
кластеризации и передаче в LE.

несколько часов пришлось признать затронутость Mk4/Mk5/Q (хотя, как
показывает наш анализ, Mk4 не поддаётся практическому brute-force
благодаря SE reseed). Во-вторых, публичная оценка "~72 бита" занижает
тяжесть на порядки: фактическая эффективная энтропия Mk3 составляла
~19-20 бит (Раздел 2.2, 4.6). Разница между 72 и 20 битами — это разница
между "теоретически ослабленным, но практически стойким" и "тривиально
взламываемым на одной GPU за минуты".

5A.3 Патч и post-hotfix bricking
--------------------------------------------------------------------------------

Патч 4.2.0 (для Mk3, выпущен 31 июля 2026) устраняет корневую причину,
включая аппаратный TRNG. Отдельно отмечается инцидент post-hotfix
bricking, связанный с последующими изменениями (PR #693, merged 5 августа
2026): часть устройств после обновления временно переставала загружаться.

Наша оценка: это transient DoS (временный отказ обслуживания), а НЕ
перманентная порча устройства. Устройства восстанавливаются; данное
поведение не эквивалентно потере ключей и не должно смешиваться с
основной уязвимостью RNG. Тем не менее, messaging Coinkite вокруг этого
инцидента следует уточнить, чтобы не провоцировать панику среди
пользователей, чьи устройства не были скомпрометированы (например,
пользователей passphrase или dice-roll).

5A.4 Затронутые и незатронутые продукты — уточнение
--------------------------------------------------------------------------------

Важно чётко разграничить периметр, чтобы пользователи не приняли ложных
решений:

  - TAPSIGNER, OPENDIME, SATSCARD: отдельные кодовые базы, НЕ затронуты.
  - Пользователи BIP-39 passphrase: базовый seed предсказуем, но passphrase
    добавляет внешнюю энтропию в PBKDF2, поэтому итоговые ключи НЕ были
    украдены. Однако такой адрес мог попасть в victim list, если он
    фигурировал в sweep-транзакции (ложноположительное включение).
  - Пользователи dice-roll: энтропия из физического источника, seed НЕ
    предсказуем, средства в безопасности.
  - Mk1/Mk2 до v4.0.0: вне регрессии, НЕ затронуты.

6.8 Экономика атаки (attacker cost model)
--------------------------------------------------------------------------------

Асимметрия затрат и выгоды в этом инциденте экстремальна и объясняет, почему
эксплуатация была рентабельна даже в фазе "медленного обескровливания":

  ЗАТРАТЫ АТАКУЮЩЕГО (единоразовые + операционные):
    - Reverse-engineering прошивки и модели PRNG: недели работы аналитика.
    - Разработка GPU-сканера (аналог нашего): дни-недели.
    - Compute для полного перебора: ~1.56 млрд кандидатов при ~134K/с =
      единицы часов на одной GPU. При облачной аренде GPU — десятки долларов.
    - Мониторинг blockchain (Electrum/собственный узел): копеечная
      операционная стоимость на протяжении лет.

  ВЫГОДА:
    - Gross-периметр 10,950 BTC, реально извлечено (Net) 5,080 BTC (~$399M).
    - Даже ранний бот в одиночку провёл 51.07 BTC (~$4M по текущему курсу)
      через единственный крупный drain.

  СООТНОШЕНИЕ ROI: при затратах на compute порядка десятков-сотен долларов
  и выгоде в сотни миллионов долларов отдача измеряется множителем 10^6 и
  выше. Это качественно объясняет:
    - терпеливость (нет давления окупать инфраструктуру);
    - масштаб копикэтов после disclosure (порог входа тривиален — любой,
      кто прочитал root cause analysis, мог за часы собрать сканер);
    - минимальное отмывание на ранней фазе (нет спешки обналичивать).

Оборонительное следствие: стоимость НАШЕГО (white-hat) полного аудита того
же порядка, что и атака, — единицы часов GPU на этап brute-force и ~1.8 часа
на deep-деривацию. Именно эта дешевизна позволила достичь 99%+ покрытия
восстановимой популяции и получить полный граф для передачи в LE. Тот же
низкий порог, что сделал атаку возможной, делает возможной и полную
форензику.

6.10 Forward tracing + haircut taint (сколько украдено ЛЕЖИТ vs ОБНАЛИЧЕНО)
--------------------------------------------------------------------------------

Ключевой вопрос для LE: сколько похищенного ещё на цепи (заmoroжаемо), а
сколько дошло до бирж. Ответ требует трассировки ВПЕРЁД от каждого адреса
жертвы через несколько хопов до терминала.

Форвард-краул: 35,189 жертв -> 5 хопов вперёд по исходящим транзакциям.
  - 39,202 узла, 3.81M рёбер
  - Терминалы: HOLDING (баланс > 0.001 BTC = лежит), SERVICE (>800 tx =
    биржа/сервис = точка обналичивания), DEADEND, MAXHOP
  - 2,783 SERVICE-эндпоинта (биржи/сервисы, с учётом targeted expansion)
  - Value-weighted (следуем за крупнейшими потоками), кап TOP_K=8000/хоп по
    объёму BTC с логированием отсечённого (принцип "no silent caps")

ПРОБЛЕМА наивной трассировки: приписывание потоку ВСЕГО баланса нижестоящего
адреса даёт абсурд. Биржевые cold-кошельки (55,000 и 36,000 BTC чужих
средств) попадали в "holding" -> сумма 292,841 BTC, что физически невозможно
(весь gross-периметр = 10,950 BTC).

РЕШЕНИЕ — HAIRCUT TAINT: похищенная доля течёт по рёбрам, РАЗБАВЛЯЯСЬ на
каждом смешении. На каждом узле tainted-доля полученного делится между
выходами пропорционально стоимости; доля, осевшая в балансе, = PARKED здесь;
доля, дошедшая до SERVICE, = обналичено. Балансы бирж НЕ считаются
похищенными — только та часть tainted-потока, что реально в них влилась.

Проверка модели: bc1qx76cae... (баланс 398 BTC, Tier-2 холодное хранение,
источник — хаб bc1qc779m8) -> haircut засчитал 360 BTC как похищенное
(лёгкая дилюция). bc1qm34lsc... (баланс 11,282 BTC, tx=0) -> засчитано лишь
58 BTC tainted-потока, остальные 11,224 BTC = чужие деньги, НЕ приписаны.

6.11 Sweeper-бот — инфраструктура атакующего АКТИВНА (не post-mortem)
--------------------------------------------------------------------------------

КРИТИЧЕСКИ ВАЖНО: инфраструктура атакующего НЕ демонтирована. К адресам
жертв привязан автоматический sweeper-бот, который мониторит балансы и
мгновенно выводит любое новое поступление на кошельки атакующего.

Три независимых доказательства (по всем 35,189 адресам, on-chain):
  1. 460 свипов в ТОМ ЖЕ блоке (задержка funding->drain = 0, block-
     granularity) + 393 за <1 минуты. Человек физически не может так
     реагировать -> автоматизированный бот.
  2. 358 адресов с ПОВТОРНЫМИ циклами fund->drain->fund->drain. Рекорд —
     170 циклов на одном адресе. Доказывает НЕПРЕРЫВНЫЙ мониторинг, а не
     разовый sweep.
  3. Same-block свипы фиксируются во ВСЕ годы 2021->2026 -> бот работает
     непрерывно 5+ лет.

Последний зафиксированный свип: 2026-08-19 (за 6.7 дней до даты анализа) ->
бот АКТИВЕН на момент публикации. Любой новый депозит на любой из 35,189
адресов будет украден в течение секунд-минут.

Следствие для приоритета: это НЕ только post-mortem завершённой кражи, а
ПРОДОЛЖАЮЩАЯСЯ активная угроза. Требуется немедленное предупреждение жертв

7. КОРНЕВАЯ ПРИЧИНА (ROOT CAUSE)
================================================================================

7.1 Классификация бага
--------------------------------------------------------------------------------

Корневой баг (сборочный флаг, отключивший аппаратный TRNG в пути генерации
seed) технически является composition error — непреднамеренной ошибкой
конфигурации, а не заведомо внедрённым бэкдором. Доказательств намеренного
бэкдора нет.

7.2 Архитектурные / процессные факторы (технические факты)
--------------------------------------------------------------------------------

  1. Security-critical криптокод (генератор энтропии) разрабатывался и
     мержился без независимого external review — нарушение принципа
     Separation of Duties (автор кода не должен быть его единственным
     ревьюером).
  2. Уязвимость оставалась в открытом коде ~5 лет, не найденная white-hat
     сообществом. Запутанная цепочка вызовов скрывала её от публичного аудита.
  3. Задокументировано 27+ месяцев pre-disclosure эксплуатации (по on-chain
     timestamps блоков).

7.3 О персональной атрибуции
--------------------------------------------------------------------------------

Настоящий отчёт НЕ выдвигает и НЕ подтверждает персональную атрибуцию
ответственности за баг. Установление конкретных лиц, их ролей и правовая
квалификация действий — исключительно задача независимой верификации и
компетентных органов (правоохранительных / судебных). Документ ограничивается
техническими фактами: наличием бага, оценкой энтропии, масштабом ущерба и
доказанным on-chain timeline.

7A.2 Почему публичные оценки систематически ниже
--------------------------------------------------------------------------------

Три структурных фактора объясняют разрыв:

  1. ВРЕМЕННОЕ ОКНО. Galaxy и BlockSec анализировали видимые пост-раскрытые
     волны (июль-август 2026). Они видели верхушку айсберга — финальный
     массовый sweep. Наш seed-recovery вскрыл 5.3 года скрытой, медленной
     эксплуатации (март 2021 - август 2026), включая 201 волну Фазы 1,
     невидимую в момент публичного disclosure.

  2. НЕПОЛНЫЙ СПИСОК ЖЕРТВ. Публичные списки строились из адресов, о которых
     сообщили сами жертвы, или из адресов, фигурировавших в sweep-TX.
     Список 6,541 адреса покрывает лишь ~18.6% реального периметра. Change-
     адреса, receive-адреса высоких индексов (1001-10000) и адреса
     дополнительных аккаунтов в эти списки не попадали. Наша deep-деривация
     до индекса 10,000 восстановила все 35,189 адресов множества наших
     seeds.

  3. GROSS против NET. Наш Gross (10,950 BTC) намеренно является верхней
     границей объёма, прошедшего через скомпрометированные ключи, включая
     change-cycling. Прямое сравнение публичных оценок следует вести с
     нашим Net (5,080 BTC) — метрикой фактического ущерба, очищенной от
     внутренних переводов через полный TX-граф.

--------------------------------------------------------------------------------

Рекомендуемая формулировка для отчётов и коммуникации с LE, не
противопоставляющая наш аудит публичным аналитикам:

7A.4 Разбор оценки BlockSec подробно
--------------------------------------------------------------------------------

BlockSec — наиболее технически глубокий из публичных отчётов, поэтому его
расхождения с нашими данными разобраны отдельно:

  - Энтропия 2^40.69: моделирует пространство состояний PRNG, а не входную
    энтропию. Наша эмпирическая оценка ~2^19-20 (Раздел 4.6). Расхождение
    методологическое, не фактическая ошибка.
  - Таймлайн с 30 июля: не покрывает 27 месяцев pre-disclosure
    эксплуатации, зафиксированной нами on-chain (ранний бот с апреля 2024).
  - Paper wallet вектор: BlockSec его не рассматривает. Мы проверили его
    (P0 GPU-скан, 1.56 млрд кандидатов) — 0 хитов в текущем victim list,
    что оставляет вопрос открытым (возможно gap в списке, а не отсутствие
    затронутых paper wallets).
  - Оценка BTC 1,405-2,055: соответствует видимым волнам; наш Net 5,080 BTC
    учитывает всю глубину периметра.

8.1 Для пострадавших (migration guide)
--------------------------------------------------------------------------------

  1. Проверьте, работало ли устройство на прошивке 4.0.1 — 4.1.9.
  2. Если да — ВСЕ seed'ы, сгенерированные на этом устройстве,
     скомпрометированы, включая paper wallets.
  3. Сгенерируйте новый seed на исправленном устройстве (прошивка 4.2.0+),
     ИДЕАЛЬНО — с использованием dice-roll энтропии или BIP-39 passphrase.
  4. Переведите ВСЕ средства на новый кошелёк немедленно — даже если
     средства ещё не украдены, атакующий может продолжать мониторинг.
  5. Не полагайтесь на BIP-39 passphrase как единственную защиту старого
     seed'а: passphrase добавляет энтропию, но базовый seed остаётся
     предсказуемым.
  6. КРИТИЧЕСКОЕ ПРЕДУПРЕЖДЕНИЕ: НЕ пополняйте старые адреса ни на какую
     сумму. К адресам жертв привязан АКТИВНЫЙ автоматический sweeper-бот
     (последний свип 2026-08-19, задокументированы 460 свипов в том же
     блоке): любой новый депозит будет украден в течение секунд-минут.
     Это не остаточный риск, а действующая инфраструктура (см. 6.11).

     реагирования.

8.3 Для индустрии (lessons learned)
--------------------------------------------------------------------------------

  1. Аппаратный RNG должен быть включён по умолчанию; отключение должно
     быть невозможным без явного #error.
  2. Ошибки препроцессора вида #define X (0) vs #define X (1) — это класс
     silent misconfiguration bugs; компиляторы должны предупреждать, а
     критичные макросы — проверяться на значение (#if X != 1), а не на факт
     определения (#ifndef).
  3. Separation of Duties для криптографического кода: автор не может быть
     единственным ревьюером; псевдонимы в security-critical контрибуциях
     недопустимы.
  4. Bloom filter на основе ВСЕХ исторических адресов (а не только текущих
     балансов) критичен для forensic-полноты — балансовый снапшот скрывает
     дренированные адреса жертв.
  5. Deep address derivation (>1000 индексов) необходим для захвата
     change-адресов и high-index паттернов использования.

8.4 Предупреждение о новых поступлениях (для бирж и координаторов)
--------------------------------------------------------------------------------

Поскольку sweeper-бот атакующего остаётся активным, любое новое поступление
на 35,189 адресов будет немедленно похищено. Профильные организации (биржи,
блокчейн-аналитические фирмы, правоохранительные органы) технически способны
организовать раннее предупреждение о поступлениях (например, подписка на
адреса через Electrum). Это отраслевая рекомендация; автор настоящего отчёта
такого наблюдения не ведёт и никаких операций с адресами не совершает.

ПРИЛОЖЕНИЕ G — ГЛОССАРИЙ ТЕХНИЧЕСКИХ ТЕРМИНОВ
--------------------------------------------------------------------------------

  BIP-32       Иерархическая детерминированная деривация ключей (HD wallet).
               Из одного master key выводится дерево дочерних ключей.
  BIP-39       Стандарт мнемонических фраз. Энтропия -> список слов (12/24) ->
               512-битный seed через PBKDF2-HMAC-SHA512 (2048 итераций).
  BIP-44/49/84/86  Стандарты путей деривации для разных типов адресов:
               44 = legacy (1...), 49 = P2SH-SegWit (3...),
               84 = Native SegWit / P2WPKH (bc1q...), 86 = Taproot (bc1p...).
  Bloom filter Вероятностная структура принадлежности множеству. Даёт
               "точно нет" или "возможно да" (с контролируемым FP rate).
  Change-адрес Адрес, на который кошелёк возвращает сдачу при трате UTXO.
               Генерируется автоматически по ветви change=1 того же seed.
  DRAINED      Статус адреса: текущий баланс 0 при наличии истории
               транзакций (средства поступали и были выведены).
  Entropy (энтропия)  Мера непредсказуемости. Идеальный seed = 256 бит;
               уязвимый Mk3 = ~19-20 эффективных бит.
  Externaldeposit  Поступление на адрес жертвы извне периметра V. В TX-graph
               классификации засчитывается как реальный (украденный) объём.
  FP rate      False positive rate — доля ложных срабатываний bloom filter.
  Gross        Суммарный total_received по всем адресам, включая внутренние
               переводы (верхняя граница объёма).
  H160 / hash160  RIPEMD160(SHA256(pubkey)) — 20-байтный хэш, ядро адреса.
  Internal transfer  Перевод между адресами одного периметра (change
               cycling). Не является украденным объёмом.
  KDF          Key Derivation Function (здесь PBKDF2-HMAC-SHA512).
  mc24w        Mini-ceremony 24-word: способ генерации seed на устройстве,
               основной продуктивный вектор brute-force.
  Net Stolen   Чистый украденный объём = external + mixed депозиты
               (Gross минус internal transfers).
  PAD          32-битное слово состояния Yasmarang; на Mk3 = UID ^ SysTick,

  pc24w        Pin-ceremony 24-word: путь генерации с вводом PIN.
               Полностью просканирован, новых seed не дал.
  PRNG         Pseudo-Random Number Generator (программный, детерминирован).
  P2WPKH       Pay-to-Witness-Public-Key-Hash — Native SegWit (bc1q).
  SE           Secure Element (ATECC608B / DS28C36B). В Mk4 добавляет reseed.
  SKIP         Число прокруток PRNG от reseed до фиксации энтропии seed;

  sha256d      Двойной SHA-256: SHA256(SHA256(x)).
  SysTick      Системный таймер ARM Cortex-M; SysTick->VAL используется в pad.
  TRNG         True Random Number Generator (аппаратный, RNG->DR). Именно его

     secure notes, seed XOR, cloning ECDH) не были доступны для аудита;
     теоретически они могут использовать тот же уязвимый PRNG.
  3. P2SH-адрес 2022 года (3LY6Wfeq...) требует отдельной трассировки для
     окончательного подтверждения даты начала работы бота.
  4. Атрибуция акторов Фазы 2 (15-25+ копикэтов) не выполнялась —
     это задача LE с использованием subpoena power к CEX/провайдерам.
  5. Оценка недостижимой популяции (Mk4/dice/passphrase, ~700-1500 seeds)
     является диапазонной и не поддаётся точному измерению нашим методом.

Этические границы. Восстановленные мнемоники и приватные ключи не
публикуются и не передаются никому, кроме уполномоченных получателей
(LE / форензик-партнёры). Поскольку все 35,189 адресов уже дренированы
(баланс 0), восстановление seed не создало нового риска для жертв. Автор
не ведёт наблюдения за этими адресами и не совершает с ними никаких
транзакций; отчёт носит исключительно исследовательский и предупредительный
характер.
